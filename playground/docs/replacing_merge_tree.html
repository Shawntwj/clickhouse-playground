ReplacingMergeTree — Visual Guide

How ClickHouse handles updates when it can't edit rows in place

1 — ClickHouse can't edit a row in place

Columnar databases like ClickHouse write data in large immutable blocks called parts. Once written, a part is never modified. This makes writes extremely fast (just append a new part) and reads fast (scan sorted columns sequentially). But it creates a problem: how do you update a value?

❌ What ClickHouse can't do
-- You cannot do this efficiently:
UPDATE datacapture.hkpug5ii1l25n
SET value_mw = 318.9
WHERE duid = 'LKBANK1'
  AND interval_utc = '2026-06-07 10:00';

-- ALTER TABLE ... UPDATE exists but
-- it rewrites entire parts — very slow,
-- not designed for frequent use.
✅ What ClickHouse does instead
-- Just INSERT a new row with a
-- higher version number:
INSERT INTO datacapture.hkpug5ii1l25n
VALUES (
    'LKBANK1',
    '2026-06-07 10:00',
    318.9,   -- corrected value
    'NSW1',
    2        -- version bumped to 2
);
This is the fundamental trade-off: ClickHouse trades write simplicity (just append) for read complexity (deduplicate on read). ReplacingMergeTree is the engine that manages this deduplication.

2 — What a "part" is

Every INSERT creates a new part — a folder on disk containing one file per column, sorted by the table's ORDER BY key. ClickHouse merges parts in the background to keep the number of parts manageable.

At this point, LKBANK1 at 10:00 has two versions on disk. The table is correct in the sense that version 2 is the truth — but nothing has cleaned up version 1 yet. That cleanup happens two ways: background merge (automatic) or FINAL (on read).

3 — Background merge: the automatic cleanup

ClickHouse constantly runs background merges — it picks two or more parts, merges them into one sorted part, and deletes the originals. During a merge of ReplacingMergeTree, it deduplicates: for rows with the same ORDER BY key, only the highest version survives.

After a successful merge, LKBANK1 v1 is gone from disk. Queries no longer need to deduplicate.

⚠️ The catch: merges are not instant. Between the time data is written and when the background merge runs (could be seconds, could be minutes), both versions exist on disk. If you query during that window without FINAL, you get duplicate rows.

4 — FINAL: deduplication on demand

FINAL tells ClickHouse: "don't wait for a background merge — deduplicate right now, at read time." It guarantees you always get the correct latest version, regardless of merge state.

5 — Why it's called "Replacing" MergeTree

1
MergeTree — the base engine. Stores data in sorted parts, merges them in the background. No deduplication.
2
ReplacingMergeTree — extends MergeTree with one rule: during a merge, if two rows share the same ORDER BY key, replace the one with the lower version. Hence the name.
3
SharedReplacingMergeTree — ClickHouse Cloud version. Same behaviour, but parts are stored in shared object storage (S3-compatible) instead of local disk, so multiple nodes can read the same data. In your playground this maps back to plain ReplacingMergeTree.
The ORDER BY clause is the deduplication key — not a primary key in the SQL sense. Two rows are considered "the same logical row" if and only if their ORDER BY columns match. In hkpug5ii1l25n that's (model_run_datetime_utc, id, interval_utc, duid, region, fuel_type) — all six columns must match for a row to be considered a duplicate.

6 — Why production wraps everything in read.* views

Instead of requiring every consumer to remember to write FINAL, production created a read database with one view per raw table — each view adds FINAL automatically. Any query on read.* is guaranteed to see deduplicated data.

⚠️ The problem: 982 raw tables × 1 read view each = 982 permanent FINAL queries. Every panel in every dashboard, every join in every derived view, hits ReplacingSorted. That's fine for large tables where you need FINAL. But small reference tables (27-row config tables, 19-row counterparty lists) don't need live dedup on every read — they barely change. That's the waste the dictionary exercises fix.
