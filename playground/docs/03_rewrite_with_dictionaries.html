Two patterns. Three rewrites. One dictGet.

Take the queries that currently JOIN through the read.* FINAL layer and rewrite them to call dictGet on the dictionaries from exercise 02. The schema stays the same; the cost graph flips upside down.

0 · The pattern

Before / after, mechanical

  BEFORE:                                   AFTER:
  JOIN read.<small_table> t ON ...           dictGet('db.dict_name', 'col', key)
       │                                          │
       └─ hits FINAL layer                       └─ hits in-RAM hash table
          rebuilds hash table per query             O(1) lookup, loaded once

Three rewrites

Example AIs a date a trading holiday?

BEFORE — JOIN through the FINAL layer

SELECT
    d.date_key,
    h.holiday_name,
    h.is_partial
FROM stg.date d
LEFT JOIN read.trading_holiday h
    ON d.date_key = h.date
   AND h.area     = 'NSW1'
   AND h.calendar = 'AEMO'
WHERE d.date_key >= today() - 30
ORDER BY d.date_key;

AFTER — dictGet on the in-memory dictionary

SELECT
    date_key,
    dictGet('tech.trading_holiday_dict', 'holiday_name', (date_key, 'NSW1', 'AEMO')) AS holiday_name,
    dictGetOrDefault('tech.trading_holiday_dict', 'is_partial', (date_key, 'NSW1', 'AEMO'), toUInt8(0)) AS is_partial,
    dictHas('tech.trading_holiday_dict', (date_key, 'NSW1', 'AEMO'))                 AS is_holiday
FROM stg.date
WHERE date_key >= today() - 30
ORDER BY date_key;

Note the tuple key: (date_key, 'NSW1', 'AEMO'). COMPLEX_KEY_HASHED layouts always lookup by tuple.
Note dictGetOrDefault: returns 0 if the date isn't a holiday, rather than the silent default of dictGet. Production code should always use the Or-Default form unless missing-key panic is desired.

Example BEnrich dispatch data with generation unit metadata.

BEFORE — FINAL join on generation_units

SELECT
    d.interval_utc,
    d.duid,
    d.value_mw,
    u.fuel_type,
    u.capacity_mw,
    u.owner
FROM read.hkpug5ii1l25n d
LEFT JOIN read.generation_units u ON d.duid = u.unit_id
WHERE d.interval_utc >= now() - INTERVAL 1 DAY
LIMIT 1000;

AFTER — dictGet replaces the join entirely

SELECT
    interval_utc,
    duid,
    value_mw,
    dictGetOrDefault('nz.generation_units_dict', 'fuel_type',   duid, 'Unknown')     AS fuel_type,
    dictGetOrDefault('nz.generation_units_dict', 'capacity_mw', duid, toFloat64(0))  AS capacity_mw,
    dictGetOrDefault('nz.generation_units_dict', 'owner',       duid, 'Unknown')     AS owner
FROM read.hkpug5ii1l25n
WHERE interval_utc >= now() - INTERVAL 1 DAY
LIMIT 1000;

HASHED() layout takes the bare key (here duid, a String), not a tuple. Three dictionary calls per row sounds expensive — it isn't. In RAM, each is a hash probe.

Example CReplace a derived view with a dict-backed version.

This is the highest-leverage rewrite: a view that downstream consumers use, now FINAL-free.

CREATE OR REPLACE VIEW au.dispatch_enriched AS
SELECT
    interval_utc,
    region,
    duid,
    value_mw,
    forecast_mw,
    -- fuel_type comes from the dictionary — no FINAL join
    dictGetOrDefault('nz.generation_units_dict', 'fuel_type',   duid, fuel_type)    AS fuel_type,
    dictGetOrDefault('nz.generation_units_dict', 'capacity_mw', duid, toFloat64(0)) AS capacity_mw,
    -- holiday flag comes from the dictionary — no FINAL join
    dictHas('tech.trading_holiday_dict', (toDate(interval_utc), region, 'AEMO'))    AS is_holiday
FROM read.hkpug5ii1l25n;

SELECT * FROM au.dispatch_enriched LIMIT 10;

Every consumer of au.dispatch_enriched now skips two FINAL joins. If this view is used by 20 downstream consumers across dashboards, that's 20 query patterns simultaneously sped up by a single DDL change.

2 · The dict-function cheat sheet
FunctionReturnsUse when
dictGet(d, col, key)Value or silent defaultYou know the key exists (PK reference). Production: avoid.
dictGetOrDefault(d, col, key, fallback)Value or your fallbackProduction. Explicit semantics for missing keys.
dictHas(d, key)UInt8 (0/1)Boolean "is this key in the dict" (e.g. holiday flag).
dictGetOrNull(d, col, key)Value or NULLYou want NULL semantics for missing.
3 · Gotchas

What experts know

Trap Composite-key dictionaries need TUPLE lookups. Forget the tuple parens and you get a confusing type-mismatch error: dictGet('d', 'col', a, b, c) ≠ dictGet('d', 'col', (a, b, c)).
Trap The simple-key dict expects the source's exact key type. If the dict's unit_id is String in source, pass a String, not toUInt64(...). The opposite of the lab's UInt16 example.
Pattern Replacing views beats rewriting queries. Don't ask 20 dashboard authors to refactor their SQL. Replace the view they all read; their queries get faster automatically.
