Wrap the small tables as dictionaries.

The §4a candidate tables — tech.trading_holiday, utl.kafka_crossdb_connectors, nz.generation_units — are small (27 to 1,922 rows), slowly-changing, and currently served through read.* FINAL. They are textbook dictionary candidates: load into RAM once, refresh on a schedule, look up in O(1).

0 · The point

Three dictionaries that retire three FINAL paths

Each dictionary in this exercise replaces a JOIN-via-FINAL pattern with a function call. Total RAM cost: well under a megabyte. Latency improvement on every consumer query: typically 3–10×.

The right layout matters: single-key tables get HASHED(); multi-column keys need COMPLEX_KEY_HASHED() and tuple lookups. This exercise has both.

1 · Run it

Three dictionaries

Step 1tech.trading_holiday_dict — composite key.

1,922 rows. Key: (date, area, calendar). Refresh every 5–10 min.

CREATE DICTIONARY IF NOT EXISTS tech.trading_holiday_dict (
    date            Date,
    area            String,
    calendar        String,
    holiday_name    String,
    is_partial      UInt8
)
PRIMARY KEY date, area, calendar
SOURCE(CLICKHOUSE(
    TABLE   'trading_holiday'
    DB      'tech'
    USER    'admin'
    PASSWORD 'admin'
))
LAYOUT(COMPLEX_KEY_HASHED())
LIFETIME(MIN 300 MAX 600);
Step 2utl.kafka_connectors_dict — composite key, rarely changes.

27 rows. Wider refresh interval (10–60 min) — the source rarely changes.

CREATE DICTIONARY IF NOT EXISTS utl.kafka_connectors_dict (
    table_schema    String,
    table_name      String,
    kafka_topic     String
)
PRIMARY KEY table_schema, table_name
SOURCE(CLICKHOUSE(
    TABLE   'kafka_crossdb_connectors'
    DB      'utl'
    USER    'admin'
    PASSWORD 'admin'
))
LAYOUT(COMPLEX_KEY_HASHED())
LIFETIME(MIN 600 MAX 3600);
Step 3nz.generation_units_dict — simple key.

111 rows. Single-key lookups (unit_id → attributes). Flat HASHED() is fastest.

CREATE DICTIONARY IF NOT EXISTS nz.generation_units_dict (
    unit_id             String,
    unit_name           String,
    fuel_type           String,
    capacity_mw         Float64,
    owner               String,
    region              String
)
PRIMARY KEY unit_id
SOURCE(CLICKHOUSE(
    TABLE   'generation_units'
    DB      'nz'
    USER    'admin'
    PASSWORD 'admin'
))
LAYOUT(HASHED())
LIFETIME(MIN 300 MAX 900);
Step 4Verify all loaded.
SELECT
    database, name, status,
    element_count, bytes_allocated,
    last_successful_update_time
FROM system.dictionaries
ORDER BY database, name;

All three rows should read status = LOADED. Total bytes_allocated across all three: ~tens of KB. Compare that to the cost of one FINAL query on the 4.8B-row production table.

2 · Choose the right LAYOUT
LayoutWhen
HASHEDSingle integer/string key, fits in RAM. Default for small dims.
COMPLEX_KEY_HASHEDMulti-column key. Lookups pass tuples: (d, 'NSW1', 'AEMO').
FLATDense integer keys (0..N). Fastest, smallest, narrow applicability.
CACHE / COMPLEX_KEY_CACHESource too big for RAM. LRU cache; misses hit source.
3 · Gotchas

What experts know

Trap Source credentials are embedded in DDL. USER 'admin' PASSWORD 'admin' in plaintext. For production, use named connection profiles (SOURCE(CLICKHOUSE(NAME 'src_admin'))) so credentials live in config, not metadata.
Trap COMPLEX_KEY_HASHED requires tuple-typed lookups. dictGet('d', 'col', (key1, key2, key3)) — not dictGet('d', 'col', key1, key2, key3). The two look interchangeable until they aren't.
Pattern LIFETIME(MIN x MAX y) jitters refresh. ClickHouse picks a uniform random time in [x, y]. Useful when many dictionaries share a slow source — staggers the load instead of stampeding.
4 · In Grafana

Open Grafana → Query Performance. The Dictionary Memory panel (or equivalent) shows new dictionaries appearing as they load. Each line in the table represents an active dictionary; size reveals memory cost.
