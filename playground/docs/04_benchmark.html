0 · The point

Tag queries so the dashboard can sort them

ClickHouse records the raw SQL in system.query_log. Add a comment like -- label: final_join to each variant — the Grafana panels can then filter by that string and put the two approaches side by side.

1 · Run it

Two rounds, one comparison

Round 1FINAL join (baseline).
-- label: final_join
SELECT
    toStartOfHour(d.interval_utc)     AS hour_utc,
    d.region,
    avg(d.value_mw)                   AS avg_mw,
    any(h.holiday_name)               AS holiday_name
FROM read.hkpug5ii1l25n d
LEFT JOIN read.trading_holiday h
    ON toDate(d.interval_utc) = h.date
   AND d.region                = h.area
   AND h.calendar              = 'AEMO'
GROUP BY hour_utc, d.region
ORDER BY hour_utc DESC
LIMIT 100;
Round 2Dictionary lookup (optimized).
-- label: dict_lookup
SELECT
    toStartOfHour(interval_utc)                                                        AS hour_utc,
    region,
    avg(value_mw)                                                                      AS avg_mw,
    dictGetOrDefault('tech.trading_holiday_dict', 'holiday_name',
        (toDate(interval_utc), region, 'AEMO'), '')                                    AS holiday_name
FROM read.hkpug5ii1l25n
GROUP BY hour_utc, region, holiday_name
ORDER BY hour_utc DESC
LIMIT 100;
CompareOne query against query_log.

Wait ~1 minute for both queries to finish and the log to settle, then:

SELECT
    if(query LIKE '%final_join%',   'final_join',
       if(query LIKE '%dict_lookup%', 'dict_lookup', 'other')) AS approach,
    count()                       AS runs,
    avg(query_duration_ms)        AS avg_ms,
    min(query_duration_ms)        AS min_ms,
    max(query_duration_ms)        AS max_ms,
    avg(memory_usage) / 1e6       AS avg_memory_mb,
    avg(read_rows)                AS avg_rows_read
FROM system.query_log
WHERE event_date = today()
  AND type    = 'QueryFinish'
  AND (query LIKE '%final_join%' OR query LIKE '%dict_lookup%')
GROUP BY approach
ORDER BY approach;

Two rows. dict_lookup should win across the board:
• avg_ms: typically 3–10× lower
• avg_memory_mb: lower, often by ≥ 2× (no hash table for the JOIN)
• avg_rows_read: the same for both (the fact table is the bottleneck) — but with FINAL it includes the JOIN's right side, which now disappears

2 · Bonus — dictionary overhead

The other side of the trade

SELECT
    name,
    status,
    element_count,
    round(bytes_allocated / 1e3, 1)   AS kb_in_memory,
    load_duration_ms,
    last_successful_update_time
FROM system.dictionaries
ORDER BY bytes_allocated DESC;

All three dictionaries together: tens of KB of RAM, single-millisecond load. The latency-vs-memory trade is laughably one-sided — and the dictionary keeps itself fresh via LIFETIME, no pipeline code needed.

4 · Gotchas

What experts know

Trap First-run latency lies. The very first call may include a dictionary load. Discard the first sample or run a warmup query before measuring.
Trap Cache effects favor the second query you run. Drop the mark cache between rounds (SYSTEM DROP MARK CACHE) and alternate the order — measure each variant cold and warm.
Pattern Bring the query_log table into your PR. Real numbers from this query are unambiguous. "10× faster" lands harder than "should be faster".
