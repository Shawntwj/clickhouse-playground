What does SELECT FINAL actually cost?

All 982 read.* views in production are SELECT * FROM datacapture.<topic> FINAL. Before deciding to replace them with dictionaries, you need to see the tax — in milliseconds, memory, and rows read — on your local replica. That's this exercise.

File · playground/exercises/01_understand_final.sql Reading · ~10 min Level · Diagnostic Prereq · make up && make playground-seed
0 · The point

Why FINAL is the hotspot

Production tables are SharedReplacingMergeTree (locally: ReplacingMergeTree). They deduplicate by version — but only eventually, when the background merge happens. Until then, multiple rows with the same key sit on disk.

FINAL forces the engine to deduplicate at read time. That means: merge-sort across all parts, drop superseded rows, and only then return results. It's correct. It's also the single most expensive thing your fleet does, because every read.* view inherits it.

The goal: measure the cost concretely, then go to exercise 02 (dictionaries) and exercise 04 (benchmark) to fix it.

1 · Mental model

What FINAL does, mechanically

datacapture.hkpug5ii1l25n             (ReplacingMergeTree(version))

 part_A                  part_B                  part_C
 ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
 │ key=1 v=1    │        │ key=1 v=2    │        │ key=3 v=1    │
 │ key=2 v=1    │        │ key=2 v=3    │        │ key=4 v=1    │
 └──────────────┘        └──────────────┘        └──────────────┘

 plain SELECT  ─────────►  read every row, return 6 rows         WRONG ANSWER
                            (duplicates because merge hasn't run)

 SELECT FINAL  ─────────►  merge-sort by key, keep MAX(version)
                            return 4 rows                         CORRECT
                            but: reads everything + sorts in memory

The shape of the cost: FINAL is roughly a sort-merge across all active parts on every read. The wider the table, the more partitions touched, the higher the tax. Memory grows with the number of parts; latency grows with rows scanned before dedup.

Three workarounds (covered in later exercises):

  • Dictionaries for small, slowly-changing dimensions — load once into RAM, look up in O(1). Exercise 02 →
  • argMax(col, version) — dedup yourself in SQL, often faster than FINAL on huge fact tables.
  • Aggregating MV — pre-dedup into a target table, dashboards read the target.
2 · Run it

The exercise

From the repo root:

# If you haven't already:
make up
make playground-seed   # ~750k rows across datacapture.* and reference tables

Then open http://localhost:8123/play (admin / admin) and work through the file. The exercise has five steps, each tagged in the SQL so Grafana's Query Performance dashboard can isolate them.

Step 1How many duplicate rows exist?
SELECT
    'hkpug5ii1l25n'                                              AS topic,
    (SELECT count() FROM datacapture.hkpug5ii1l25n)             AS raw_rows,
    (SELECT count() FROM datacapture.hkpug5ii1l25n FINAL)       AS final_rows,
    raw_rows - final_rows                                        AS duplicates;

Expect: raw_rows ≫ final_rows. With the seed data here, the merge sees ~500k inserts of which only the latest version per (model_run_datetime_utc, id, interval_utc, duid, region, fuel_type) survives. The gap is the dedup load.

Step 2EXPLAIN the FINAL pipeline.
EXPLAIN pipeline
SELECT count() FROM datacapture.hkpug5ii1l25n FINAL;

Look for ReplacingSorted and AggregatingTransform stages. That's the sort-merge cost: every active part contributes a stream, all streams get merged on the key, dedup happens, then the count runs. Compare to the same query without FINAL — far fewer processor stages.

Step 3Hit the read.* view (FINAL is inherited).
SELECT count() FROM read.hkpug5ii1l25n;

Same cost as Step 1 — the view is SELECT * FROM datacapture.hkpug5ii1l25n FINAL. Every downstream consumer pays this. This is the production reality the project is built to fix.

Step 4Time a realistic aggregation through FINAL.
SELECT
    region,
    fuel_type,
    avg(value_mw)  AS avg_mw,
    count()        AS rows
FROM read.hkpug5ii1l25n
GROUP BY region, fuel_type
ORDER BY avg_mw DESC;

Run it 3–4 times. Note query_duration_ms drifts a bit because of cache effects. The average across runs is what Grafana plots — open the Query Performance dashboard side by side.

Step 5Which tables get hit by FINAL the most?
SELECT
    tables[1]                       AS table_name,
    countIf(query LIKE '%FINAL%')   AS final_queries,
    count()                         AS total_queries,
    avg(query_duration_ms)          AS avg_ms,
    max(query_duration_ms)          AS max_ms
FROM system.query_log
WHERE event_date = today()
  AND type = 'QueryFinish'
  AND length(tables) > 0
GROUP BY table_name
ORDER BY final_queries DESC
LIMIT 20;

This is the hit list. Tables high in the list with high avg_ms are your dictionary candidates (if they're small/slowly-changing) or rollup candidates (if they're large/aggregable). Carry this list into exercise 02.

3 · Prove it

System tables to keep open alongside

QuestionQuery
Per-query memory + duration SELECT query_duration_ms, formatReadableSize(memory_usage) FROM system.query_log WHERE query ILIKE '%FINAL%' ORDER BY event_time DESC LIMIT 10
How many parts get merge-sorted? SELECT count() FROM system.parts WHERE database = 'datacapture' AND table = 'hkpug5ii1l25n' AND active
Force a real merge to shrink the tax OPTIMIZE TABLE datacapture.hkpug5ii1l25n FINAL — then re-run Step 1. Note: production-dangerous on huge tables.
Was a FINAL run parallelized? SELECT ProfileEvents['SelectedParts'], ProfileEvents['MaxFinalThreadsUsed'] FROM system.query_log WHERE query_id = '...'
4 · Gotchas

What experts know that beginners don't

Trap OPTIMIZE TABLE … FINAL "fixes" FINAL queries locally but is a lie at scale. It rewrites every part — fine on 500k rows here, catastrophic on the 4.8B-row production version. If you run it in prod, set the calendar reminder for the merge to finish.
Trap Cache makes FINAL look faster than it is. Drop the mark cache (SYSTEM DROP MARK CACHE) between runs when measuring. Otherwise you're benchmarking RAM access.
Settings do_not_merge_across_partitions_select_final = 1 and max_final_threads are the two settings that turn FINAL from "single-stream merge" into "per-partition parallel merge". On a partitioned table this is often a 4–8× speedup, free.
Pattern FINAL belongs in ad-hoc/exploration. It doesn't belong behind a dashboard. Production dashboards should read a pre-deduplicated rollup or use argMax — covered in exercise 03 and the lab's read warfare exercise.
5 · In Grafana

Where this shows up on the Query Performance dashboard

Open http://localhost:3000 → Query Performance. The dashboard is wired to system.query_log, so every step above will appear within seconds.
