ClickHouse FINAL — Visual Guide

Why it's expensive, and how dictionaries fix it

1 — What ReplacingMergeTree looks like on disk

ClickHouse writes incoming rows into parts (immutable sorted files). It merges parts in the background — but between merges, the same logical row can exist in multiple parts with different version values. That's fine at write time. The problem is at read time.

Part 1 — written 2 hours ago
duidinterval_utcvalue_mwversion
LKBANK12026-06-07 10:00312.41 old
MACGEN12026-06-07 10:0088.11
ARWF12026-06-07 10:00201.71
Part 2 — written 10 min ago (correction)
duidinterval_utcvalue_mwversion
LKBANK12026-06-07 10:00318.92 winner
VMIN12026-06-07 10:05450.01
⚠️ LKBANK1 at 10:00 exists in both parts. The correct value is 318.9 (version 2). Without FINAL you'd get both rows back. With FINAL, ClickHouse merges the streams on read and discards the loser — but it has to do this work every time you query.

2 — What FINAL does row by row

SELECT * FROM datacapture.hkpug5ii1l25n FINAL — ClickHouse reads all parts, sorts them together by the ORDER BY key, then for each unique key keeps only the row with the highest version.

This dedup step (ReplacingSorted in the EXPLAIN output) runs on every single query, across all 500k rows, on all 4 parallel threads. In production with 4.8 billion rows it's a serious bottleneck.

3 — Why every query hits FINAL (the view chain)

Every consumer reads through two layers of views. FINAL is inherited transitively — so even a simple count on a business view triggers a full dedup scan.

4 — The EXPLAIN pipeline you ran, annotated

MergeTreeSelect (InOrder) × 4 DISK
Reads 4 sorted ranges from disk in parallel.
Each range is a slice of the ORDER BY key space: e.g. (-inf → MACGEN1/VIC1) and (MACGEN1/VIC1 → +inf)
FilterSortedStreamByRange × 2
Trims each stream to its exact key boundary so streams don't overlap.
Necessary before merging — you can't dedup across overlapping ranges.
⚡ ReplacingSorted 2 → 1  ← THE HOTSPOT
Merges 2 sorted streams into 1, keeping only the highest-version row per ORDER BY key.
This is what FINAL means at the execution level. Runs on every query. Cannot be cached.
SelectByIndicesTransform
Passes only the winning rows upstream — discards the losers identified by ReplacingSorted.
AggregatingTransform × 4 → Resize → result
Runs count() across 4 threads, merges results, returns to you.

5 — The §4a small tables — why they're the worst offenders

The big datacapture tables are expensive to dedup — but they're also big enough that you expect some cost. The real waste is small reference tables being read through FINAL on every join. These rarely change, yet every query re-deduplicates them from scratch.

Every JOIN against these tables triggers a FINAL dedup scan — even though the underlying data almost never changes. A 19-row counterparty table should never cause a ReplacingSorted merge.

6 — How a dictionary fixes it

A ClickHouse dictionary loads a table into RAM once and serves lookups directly from memory. No disk read. No ReplacingSorted. No FINAL overhead. Refreshes automatically every N minutes.

tech.trading_holiday DISK

Lookup: dictGet('tech.trading_holiday_dict', 'holiday_name', (date, area, calendar))
✅ dictGet() hits RAM directly. Zero disk reads, zero FINAL dedup, sub-millisecond per row. The dictionary refreshes automatically in the background — your queries never wait for it.

7 — Before / After: the query rewrite you'll do in exercise 3

❌ Before — joins through FINAL
SELECT
    date_key,
    h.holiday_name,
    h.is_partial
FROM stg.date d
LEFT JOIN read.trading_holiday h
    ON  d.date_key = h.date
    AND h.area     = 'NSW1'
    AND h.calendar = 'AEMO'

-- read.trading_holiday is:
--   SELECT * FROM tech.trading_holiday FINAL
-- So this join triggers ReplacingSorted
-- on 1,922 rows × every query
✅ After — dictGet from RAM
SELECT
    date_key,
    dictGet(
        'tech.trading_holiday_dict',
        'holiday_name',
        (date_key, 'NSW1', 'AEMO')
    ) AS holiday_name,
    dictHas(
        'tech.trading_holiday_dict',
        (date_key, 'NSW1', 'AEMO')
    ) AS is_holiday
FROM stg.date

-- No JOIN. No FINAL. No disk read.
-- Lookup goes straight to RAM.
