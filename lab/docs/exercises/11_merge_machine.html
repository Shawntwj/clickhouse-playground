Merges are the heartbeat. Stop them to learn them.

Experts don't fear "Too many parts" — they know which knobs produce it and which relieve it. This exercise freezes merges on purpose, watches parts pile up, releases them, and observes the avalanche cleanup. Plus partition surgery (instant), mutations (slow), and the merge level shape that tells a healthy table from a sick one.

0 · The guardrails

The MergeTree settings that govern everything

SELECT name, value, description
FROM system.merge_tree_settings
WHERE name IN ('parts_to_delay_insert', 'parts_to_throw_insert',
               'max_bytes_to_merge_at_max_space_in_pool',
               'min_bytes_for_wide_part', 'old_parts_lifetime');
SettingWhat it does
parts_to_delay_insertServer starts sleeping your inserts (backpressure) once this many parts accumulate.
parts_to_throw_insertFamous Too many parts exception fires here.
max_bytes_to_merge_at_max_space_in_poolParts bigger than this stop being merged (~150 GB default).
min_bytes_for_wide_partBelow this, parts use COMPACT layout (all columns one file).
old_parts_lifetimeHow long inactive (merged-away) parts stay on disk before deletion.
1 · Run it

The merge experiment

Step 1Freeze merges.
SYSTEM STOP MERGES lab.firehose;
Step 2In your shell — induce the disease.
make storm-sync

Grafana: Active parts climbs in a straight line — nothing fights back. Around parts_to_delay_insert you'll see inserts get slower (backpressure), then the throw threshold kills them entirely.

Step 3Release the merges — watch the avalanche.
SYSTEM START MERGES lab.firehose;

-- Live view of the engine catching up:
SELECT table, elapsed, progress, num_parts,
       formatReadableSize(total_size_bytes_compressed) AS merging
FROM system.merges;
Step 4Post-mortem.
SELECT event_type, count(), avg(duration_ms) AS avg_ms
FROM system.part_log
WHERE table = 'firehose' AND event_date = today()
GROUP BY event_type;

NewPart count vs MergeParts count = your insert:merge ratio. Healthy systems merge in big steps: few merges, each combining many parts.

2 · Merge levels

The LSM-like shape

SELECT level, count() AS parts, sum(rows) AS rows
FROM system.parts
WHERE table = 'events' AND active
GROUP BY level ORDER BY level;

A settled table converges to a handful of high-level parts. Many level-0 parts hours after inserting = merges are starved (CPU? disk? too many tables sharing the pool?). This single query diagnoses most ingestion-side weirdness.

3 · Manual control

The tools you reach for

Force a merge

OPTIMIZE TABLE lab.firehose FINAL;        -- merge to ~1 part per partition
-- Expert use: nightly per-partition optimize on yesterday's data:
OPTIMIZE TABLE lab.firehose PARTITION '202606' FINAL;

Abuse warning: OPTIMIZE … FINAL on a huge hot table rewrites everything. It's a sledgehammer. Schedule it, don't reflex it.

Partition surgery (instant, metadata-only)

ALTER TABLE lab.firehose DROP PARTITION '202605';        -- instant delete
ALTER TABLE lab.firehose DETACH PARTITION '202605';      -- hide, keep on disk
ALTER TABLE lab.firehose ATTACH PARTITION '202605';      -- bring it back
ALTER TABLE t2 ATTACH PARTITION '202606' FROM lab.firehose;  -- zero-copy move

This is why PARTITION BY exists: lifecycle ops at file-system speed. DELETE FROM rewrites parts (mutations — see below).

Mutations — the slow path

ALTER TABLE lab.firehose DELETE WHERE site_id = 13;
SELECT * FROM system.mutations WHERE table = 'firehose' FORMAT Vertical;

A mutation rewrites every affected part in the background. On big tables, hours. Experts design so they never need row mutations: partition drops, TTLs, ReplacingMergeTree versions (next exercise — read warfare).

4 · Gotchas

What experts know

Trap SYSTEM STOP MERGES applies until restart OR START MERGES. Forget to start them after a debug session and you'll find the table broken next morning.
Trap OPTIMIZE FINAL doesn't always merge to one part. If parts span partitions, you get one per partition. If parts exceed max_bytes_to_merge_at_max_space_in_pool, they're left alone. Check system.parts after.
Pattern Lightweight deletes (DELETE FROM … WHERE …) write a tiny mask file instead of rewriting parts. Much faster for ad-hoc cleanup; reads check the mask transparently. Available since 23.x.
