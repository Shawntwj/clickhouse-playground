0 · The point

What changes when there's more than one node

Single-node ClickHouse needs no coordination — it's the only process touching its data directory. The moment you have two nodes, three new things appear: a coordination service (ClickHouse Keeper, the ZooKeeper replacement) that arbitrates who-owns-what, cluster definitions in config that tell each node "you are part of a group called X", and ON CLUSTER DDL that runs a CREATE/DROP on every node in one shot.

This lab's setup: 1 Keeper + 2 ClickHouse nodes (ch-1, ch-2), with TWO clusters defined over the same containers — cluster_1s2r for replication exercises and cluster_2s1r for sharding exercises. Same physical infra, two logical topologies.

2 · Run it

Five checks before you trust the cluster

Step 0Bring it up.
make up-cluster

# Sanity:
make cluster-status

Output lists both clusters with two rows each, plus a confirmation that ch-1 can talk to Keeper.

Step ASee the clusters and Keeper from ch-1.
make sql-1
SELECT cluster, shard_num, replica_num, host_name, port, is_local
FROM system.clusters
WHERE cluster LIKE 'cluster_%'
ORDER BY cluster, shard_num, replica_num;

SELECT name, value FROM system.zookeeper WHERE path = '/';

The first query returns 4 rows (2 per cluster). The second returns Keeper's root children — typically clickhouse and keeper. If system.zookeeper errors, Keeper isn't reachable; check docker logs ch-keeper.

Step BFirst ON CLUSTER DDL.
CREATE DATABASE IF NOT EXISTS lab ON CLUSTER cluster_1s2r;

Without ON CLUSTER, the database would only exist on the node you ran it on. With it, the DDL goes into a queue persisted in Keeper, both nodes pull from the queue and execute. Inspect:

SELECT host_name, query, query_create_time, exception
FROM system.distributed_ddl_queue
ORDER BY query_create_time DESC LIMIT 5;

Healthy entry: two rows (one per host), exception = '', both finished.

Step CInspect per-node macros.
SELECT macro, substitution FROM system.macros;

On ch-1: {shard}=01, {replica}=ch-1. On ch-2: {shard}=01, {replica}=ch-2. These are configured per-container in cluster/config/ch-{1,2}/macros.xml. {replica} uniquely identifies the node; {shard} is the same here because both nodes are replicas of the same shard in cluster_1s2r.

Step DVerify both nodes are healthy (preview of ex. 44).
SELECT _shard_num, hostName(), version()
FROM clusterAllReplicas('cluster_1s2r', system.one);

Two rows: ch-1 and ch-2. If one is missing, that node is down or unreachable — Keeper still works, but you've lost a replica.

3 · The DDL-via-Keeper picture
  CREATE DATABASE lab ON CLUSTER cluster_1s2r;
                  │
                  ▼
        ┌─── ch-keeper ───┐         queue stores: SQL + target hosts + status
        │  /clickhouse/   │
        │   /task_queue   │
        │      /ddl       │
        └─┬─────────────┬─┘
          │             │     each ClickHouse node polls the queue
          ▼             ▼     and executes its own copy of the DDL,
        ch-1          ch-2    then writes the result back to Keeper.

  system.distributed_ddl_queue surfaces all of this in SQL.
4 · Gotchas

What experts know

Trap Forget ON CLUSTER and your tables exist on one node only. Insidious because reads via Distributed will SILENTLY return data from only some shards. Make ON CLUSTER muscle memory for every DDL.
Trap The DDL queue can stall. If one node is down, the DDL queue entry sits with status inactive for that host. New ON CLUSTER DDLs queue up behind it. Fix the node OR delete the queue entry via Keeper: SYSTEM DROP DNS CACHE / restart strategies vary by version.
Pattern Keeper is the single point of coordination — make it HA in prod. This lab uses 1 Keeper for simplicity. Real deployments run 3 or 5 Keeper nodes with Raft consensus. Same config, just multiple <server> blocks in keeper_config.xml.
Pattern Use DROP … SYNC on cluster DDL. The default is async — DROP returns before all nodes finish. SYNC blocks until done, which is what you want in tests/CI.
