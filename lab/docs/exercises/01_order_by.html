The biggest single optimization is your ORDER BY.

ClickHouse never finds a row — it skips granules of 8192 rows using a sparse index. Whether it skips 99% of the table or scans the whole thing comes down to one choice you make once, at CREATE TABLE time, and can't change later without rebuilding.

File · lab/sql/01_seed_and_order_by.sql Reading · ~12 min Level · Fundamentals Prereq · make up
0 · The point

Why this exercise exists

Two tables with the same 20 million rows, the same query, and a ~100x difference in elapsed time. The only difference is the column order in ORDER BY. Once you've seen and explained that gap, you understand what the sparse index actually does — and most of ClickHouse query performance follows from it.

The lesson: put the columns you filter by in front, ordered low cardinality → high cardinality. Time usually goes last, not first.

1 · Mental model

How the sparse index actually works

Every MergeTree table is a stack of parts (immutable directories on disk). Each part stores columns separately, and each column file is divided into granules of 8192 rows. The "primary index" holds one entry per granule, not per row. 

part_2026_06_1_1_0/
 ├── site_id.bin       columns are files, compressed
 ├── event_time.bin
 ├── url.bin
 └── primary.idx       ONE entry per 8192 rows ("granule")
                       just the FIRST value of the ORDER BY tuple

query:  WHERE site_id = 42 AND event_time > now() - 7d

ORDER BY (site_id, event_time)          ORDER BY user_id
┌──┬──┬──┬██┬██┬──┬──┬──┬──┬──┐         ┌██┬██┬██┬██┬██┬██┬██┬██┬██┬██┐
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘         └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
   skipped     read     skipped            ALL granules selected
   ~2 granules of 2440                     20M rows scanned

The filter on site_id = 42 uses the primary index to locate two adjacent granules where 42 lives, then reads only those. The "bad" table sorts by user_id first, so the index for site_id is meaningless — every granule could contain site 42, so all of them get read.

Rules of thumb, in priority order:

  • Put filter columns in front, ordered low → high cardinality. (tenant_id, site_id, event_time) is canonical.
  • Time usually goes last among filters. Most queries are "for entity X over a time range" — entity then time.
  • PARTITION BY is for lifecycle (drops, TTL), not query speed. toYYYYMM(...) is the safe default. Hundreds of partitions = you over-partitioned.
  • You can't change ORDER BY later without rebuilding the table. Spend design time here.
2 · Run it

The exercise

From the repo root, after make up:

# Seeds both tables with the same 20M rows. ~30-60s on a laptop.
make seed

That executes lab/sql/01_seed_and_order_by.sql, which creates two tables:

-- "Bad": high-cardinality column first. Index can't prune.
CREATE TABLE lab.events_bad
(
    event_time  DateTime,
    user_id     UInt64,
    site_id     UInt64,
    country     String,
    url         String,
    duration_ms UInt64
)
ENGINE = MergeTree
ORDER BY user_id;   -- high-cardinality first = sparse index useless

-- "Good": low-cardinality prefix, time second, tight types, codecs.
CREATE TABLE lab.events
(
    event_time  DateTime CODEC(Delta, ZSTD),
    user_id     UInt32,
    site_id     UInt16,
    country     LowCardinality(String),
    url         LowCardinality(String),
    duration_ms UInt16 CODEC(T64, ZSTD)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (site_id, event_time);   -- matches "site X over time"
Step 1Same question, both tables.

Open http://localhost:8123/play (admin / admin) and run:

SELECT quantile(0.95)(duration_ms)
FROM lab.events_bad
WHERE site_id = 42 AND event_time > now() - INTERVAL 7 DAY;

SELECT quantile(0.95)(duration_ms)
FROM lab.events
WHERE site_id = 42 AND event_time > now() - INTERVAL 7 DAY;

Expect: ~100× elapsed difference. The Elapsed line and Read X rows, Y MB tail under the result are the truth-teller. The bad table reads ~20M rows; the good one reads tens of thousands.

Step 2Prove it with EXPLAIN.
EXPLAIN indexes = 1
SELECT quantile(0.95)(duration_ms)
FROM lab.events
WHERE site_id = 42 AND event_time > now() - INTERVAL 7 DAY;

Look for Granules: X/Y. On the good table, X is a tiny fraction of Y. Re-run against events_bad and watch X approach Y — that's a full scan with extra steps.

Step 3Read the receipts in the query log.
SELECT
    query_duration_ms,
    read_rows,
    formatReadableSize(read_bytes) AS read,
    tables
FROM system.query_log
WHERE type = 'QueryFinish' AND query_kind = 'Select'
  AND (has(tables, 'lab.events') OR has(tables, 'lab.events_bad'))
ORDER BY event_time DESC
LIMIT 10;

Two rows for the same logical query. The read_rows column tells the whole story: ~thousands vs ~20 million.

4 · Gotchas

What experts know that beginners don't

Trap Time-first ORDER BY feels natural but is usually wrong. ORDER BY (event_time, site_id) only helps "latest data, all sites" queries. The far more common shape — "this entity, over time" — wants entity first.
Trap PARTITION BY ≠ a way to speed up queries. It's for lifecycle ops (drop a month, TTL a partition). It also limits the optimizer's ability to merge across partitions. Hundreds of partitions slow everything down.
Trap You cannot change ORDER BY with a regular ALTER. You can MODIFY ORDER BY to add a trailing column (rare, narrow rules), but reordering the prefix means: create a new table, INSERT SELECT, swap. The cost of getting this wrong is real.
Bigger One ORDER BY can't serve every query. When two access patterns fight (site-then-time vs user-then-time), the answer is a projection (exercise 06) or a second MergeTree fed by a materialized view (exercise 05) — not a compromise ORDER BY.
