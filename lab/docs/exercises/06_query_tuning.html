When ORDER BY can't satisfy every query.

PREWHERE for cheaper filter passes; skip indexes for selective predicates on non-key columns; projections for "my second access pattern fights my ORDER BY". Three knobs after schema design, before you start adding new tables.

0 · The point

The schema decisions you can change after the fact

You can't change ORDER BY easily. You can add skip indexes, projections, and PREWHERE hints — all reversible. This exercise covers the four techniques most people forget exist, in increasing cost order.

Order of operations: verify PREWHERE works → add a skip index for selective filters → if a second access pattern dominates, add a projection → if all else fails, build a second table via MV.

1 · PREWHERE

Read filter column first, the rest only for survivors

Normally ClickHouse reads every column you select, applies WHERE, then projects. With PREWHERE it reads only the filter column, evaluates the predicate, then reads remaining columns only for surviving granules. Usually automatic — verify with EXPLAIN: 

EXPLAIN SYNTAX
SELECT url, duration_ms FROM lab.events
WHERE country = 'JP' AND duration_ms > 4900;

Look for PREWHERE in the rewritten query. If the optimizer guessed wrong, force it manually: SELECT url, duration_ms FROM lab.events PREWHERE country = 'JP' WHERE duration_ms > 4900.

2 · Skip indexes

Granule pruning for non-key columns

Secondary indexes that let CH skip granule blocks for columns NOT in the primary key. They only help selective predicates — a filter that matches 90% of rows doesn't benefit. 

ALTER TABLE lab.events ADD INDEX idx_country country TYPE set(100) GRANULARITY 4;
ALTER TABLE lab.events ADD INDEX idx_url url TYPE bloom_filter(0.01) GRANULARITY 4;
ALTER TABLE lab.events MATERIALIZE INDEX idx_country;
ALTER TABLE lab.events MATERIALIZE INDEX idx_url;

EXPLAIN indexes = 1
SELECT count() FROM lab.events WHERE url = '/checkout';
TypeBest for
minmaxSorted-ish numerics (e.g. price, timestamp not in PK)
set(N)Low-cardinality columns (~< 100 distinct values per granule)
bloom_filter(p)Strings, equality lookups, p = false-positive rate
tokenbf_v1 / ngrambf_v1Substring / token search on long text
3 · Projections

The same table, stored a second time, in a different order

A projection is exactly that — a hidden copy with a different ORDER BY or pre-aggregated. The optimizer picks it automatically. The fix for "my second query pattern fights my ORDER BY" without spinning up a new table. 

ALTER TABLE lab.events ADD PROJECTION by_user
(
    SELECT * ORDER BY user_id, event_time
);
ALTER TABLE lab.events MATERIALIZE PROJECTION by_user;

-- Now this query (terrible under ORDER BY (site_id, event_time)) is index-driven:
SELECT count(), max(event_time) FROM lab.events WHERE user_id = 12345;

EXPLAIN indexes = 1
SELECT count(), max(event_time) FROM lab.events WHERE user_id = 12345;
-- Look for "Reading from projection 'by_user'".

Cost: ~2× storage, slower inserts and merges for the table. A trade, not magic.

4 · Settings that matter

Per-query knobs you should know

-- Parallelism (default = number of cores)
SETTINGS max_threads = 4

-- Fail fast instead of OOMing
SETTINGS max_memory_usage = 2000000000      -- 2 GB

-- Spill big GROUP BY to disk instead of failing
SETTINGS max_bytes_before_external_group_by = 1000000000

Try a huge GROUP BY with and without external aggregation while watching the Memory panel:

SELECT user_id, count() FROM lab.events GROUP BY user_id
FORMAT Null
SETTINGS max_bytes_before_external_group_by = 200000000;
5 · Read your own telemetry

The "top 10 slow queries" recipe

SELECT
    normalized_query_hash,
    any(substring(query, 1, 80)) AS sample,
    count()                       AS runs,
    round(avg(query_duration_ms)) AS avg_ms,
    formatReadableSize(avg(memory_usage)) AS avg_mem,
    sum(read_rows)                AS total_rows_read
FROM system.query_log
WHERE type = 'QueryFinish' AND query_kind = 'Select'
GROUP BY normalized_query_hash
ORDER BY sum(query_duration_ms) DESC
LIMIT 10;

Run this weekly. The top entry is your highest-leverage optimization target — fix it, the whole fleet feels lighter.

6 · Gotchas

What experts know

Trap Skip indexes only help selective filters. An index that matches 80% of granules costs more (extra I/O for index files) than it saves. Always check EXPLAIN indexes=1 before keeping one.
Trap Projections silently break under heavy mutation. They're a copy of the data, so every ALTER … DELETE rewrites both the table and the projection. Use them on append-mostly tables.
Pattern force_optimize_projection = 1 errors if a projection wasn't used. The hidden gem for verifying your projection is actually working in production.
