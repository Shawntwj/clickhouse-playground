Schema is storage is speed.

Every column is a separate file on disk. Make those files smaller and every query gets faster — fewer bytes to read, decompress, and shuffle through CPU caches. This exercise is about choosing types, LowCardinality, and codecs so that the same 20M rows occupy a fraction of the bytes.

0 · The point

Why columns are files

ClickHouse stores each column in its own compressed file. When you query WHERE country = 'JP' GROUP BY url, the engine touches three files (the filter column, the group key, and any aggregated columns) and ignores everything else. Smaller files mean:

  • Less I/O — fewer bytes off disk per query.
  • Better cache locality — more rows per CPU cache line.
  • Smaller marks/index — the sparse index itself fits in RAM more easily.

Three levers, in priority order: the right type (smallest int that fits, LowCardinality for low-distinct strings), the right codec (Delta/Gorilla/T64 before ZSTD), and no reflexive Nullable.

1 · Mental model

What LowCardinality and codecs actually do

String column "country" — 20M rows, 10 distinct values
─────────────────────────────────────────────────────────
plain String:           20M × ~3 bytes UTF-8 = 60 MB raw
                        ZSTD compresses to ~4 MB

LowCardinality(String): tiny dictionary {US,DE,IN,...} + 20M × UInt8 indexes
                        = 10 strings + 20M bytes
                        ZSTD compresses to ~0.4 MB              10x smaller
                        GROUP BY runs on UInt8, not String      faster


CODEC chain on DateTime column                  raw 20M × 4 bytes = 80 MB

  Delta(4)  →  store DIFFS between adjacent timestamps (mostly tiny)
  ZSTD(1)   →  compress the diff stream                               ~3 MB

  T64       →  for ints that don't use all their bits (UInt16 in UInt64 slot)
  Gorilla   →  for floats that change slowly (gauges, prices)
  DoubleDelta → diffs-of-diffs, even better for monotonic time
  LZ4 (default) → faster, larger          ZSTD → smaller, slower

The pattern: a specialized codec exploits structure (sorted-ish, mostly-constant, narrow-int) to remove entropy, then a general codec (ZSTD) compresses the small leftover. Always specialized first, ZSTD last.

2 · Run it

The exercise

Step 1Compare per-column compression on the two tables from exercise 01.
SELECT
    table,
    name AS column,
    type,
    formatReadableSize(data_compressed_bytes)   AS compressed,
    formatReadableSize(data_uncompressed_bytes) AS uncompressed,
    round(data_uncompressed_bytes / data_compressed_bytes, 2) AS ratio
FROM system.columns
WHERE database = 'lab' AND table IN ('events', 'events_bad')
ORDER BY table, data_compressed_bytes DESC;

Things to notice:
• country: String column compresses fine; LowCardinality(String) compresses ~10× better because it stores tiny UInt8 indexes plus a 10-entry dictionary.
• event_time with CODEC(Delta, ZSTD): timestamps stored as differences compress far better than absolute values.
• duration_ms: UInt16 vs UInt64 = 4× fewer raw bytes before ZSTD even runs.

Step 2Build a third variant — beat events.
CREATE TABLE lab.events_tuned AS lab.events
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (site_id, event_time);

ALTER TABLE lab.events_tuned
    MODIFY COLUMN event_time DateTime CODEC(DoubleDelta, ZSTD(3));

INSERT INTO lab.events_tuned SELECT * FROM lab.events;

Re-run the Step 1 query for table = 'events_tuned'. DoubleDelta + higher ZSTD level squeezes the timestamp column further (diff-of-diffs near zero for evenly-spaced events). Try other moves: CODEC(T64, ZSTD) on site_id, CODEC(ZSTD(6)) globally — measure each.

3 · Cheat sheet

The codec ladder

Column shapeCodec chainWhy
Timestamps, counters, sorted-ish intsDelta, ZSTD or DoubleDelta, ZSTDAdjacent values are close → diffs are small → compress well.
Slowly-changing floats (gauges, prices)Gorilla, ZSTDXOR-encoded bit-packed floats; tiny when most rows ≈ previous row.
Small ints in a wide slotT64, ZSTDPacks ints by their actual bit-width before ZSTD.
Strings with < ~10k distinct valuesLowCardinality(String)Dictionary + UInt8/UInt16 index — smaller + faster GROUP BY.
General fallbackZSTD(1..3) (default LZ4)LZ4 = faster decompress, ZSTD = smaller. Pick the trade.
4 · Gotchas

What experts know

Trap Nullable(...) by default is expensive. It adds a hidden bitmap file per column, slowing scans even when no NULLs exist. Use sentinel values (0, '') when the column has natural absence semantics.
Trap LowCardinality on a high-cardinality column hurts. Past ~10k distinct values, the dictionary itself becomes expensive to maintain on merges. Stick to genuinely low-distinct strings.
Trap You can MODIFY CODEC on an existing column, but new compression only applies to new parts. Existing parts keep their old codec. Use OPTIMIZE TABLE … FINAL on a test partition to force rewrite, then measure.
