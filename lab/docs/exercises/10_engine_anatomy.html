The storage engine has no secrets.

Parts are directories. Columns are files. The "index" is a few hundred KB of marks. ProfileEvents records 400 counters per query. There's a built-in sampling profiler. Once you've seen all of it with your own eyes, "ClickHouse is fast" stops being magic and becomes predictable.

0 · The point

Five places experts look that beginners don't

  • Parts on disk — ls them, see column files directly.
  • system.parts — granules, marks, part_type, level.
  • Mark cache cold-vs-warm via SYSTEM DROP MARK CACHE.
  • ProfileEvents — ~400 counters per query, the single most underused expert tool.
  • Built-in sampling profiler — read your own C++ stacks.
A · Parts on disk

It's just files

# From your shell, not SQL:
docker exec clickhouse ls /var/lib/clickhouse/data/lab/events/
docker exec clickhouse ls /var/lib/clickhouse/data/lab/events/<some_part_dir>/
/var/lib/clickhouse/data/lab/events/all_1_1_0/
 ├── country.bin       compressed column data
 ├── country.cmrk2     marks: byte offsets into .bin, one per granule (8192 rows)
 ├── event_time.bin
 ├── event_time.cmrk2
 ├── primary.cidx      sparse primary index
 ├── partition.dat
 ├── count.txt         row count
 └── checksums.txt

Small parts use COMPACT (all columns in one data.bin) until ~10MB,
then switch to WIDE (per-column files) on merge.

Part name decoding:
   all_1_1_0
   │   │ │ └── merge level (0 = freshly inserted)
   │   │ └──── max block number
   │   └────── min block number
   └────────── partition id

Verify which storage type via:

SELECT name, part_type, rows, formatReadableSize(bytes_on_disk) AS size, level
FROM system.parts
WHERE database = 'lab' AND table = 'events' AND active
ORDER BY rows DESC;
B · Granules and marks

The sparse index, quantified

SELECT
    table,
    sum(marks)                                   AS total_granules,
    sum(rows)                                    AS rows,
    round(sum(rows) / sum(marks))                AS rows_per_granule,
    formatReadableSize(sum(marks) * 24)          AS approx_pk_ram
FROM system.parts
WHERE database = 'lab' AND active
GROUP BY table;

The entire primary index for 20M rows is a few hundred KB in RAM. That's why ClickHouse index lookups are essentially free — and why the index can't find individual rows, only skip 8192-row blocks.

C · Mark cache

Watch cold-vs-warm

SYSTEM DROP MARK CACHE;
SELECT count() FROM lab.events WHERE site_id = 42 FORMAT Null;  -- cold
SELECT count() FROM lab.events WHERE site_id = 42 FORMAT Null;  -- warm

SELECT
    event_time,
    query_duration_ms,
    ProfileEvents['MarkCacheHits']    AS mark_hits,
    ProfileEvents['MarkCacheMisses']  AS mark_misses,
    ProfileEvents['SelectedGranules'] AS granules_read,
    ProfileEvents['SelectedParts']    AS parts_read
FROM system.query_log
WHERE type = 'QueryFinish' AND query LIKE '%site_id = 42%' AND query_kind = 'Select'
ORDER BY event_time DESC LIMIT 4;

ProfileEvents is the single most underused expert tool. ~400 counters recorded per query. Diffing them between two query variants tells you exactly where time went. Browse them all: SELECT * FROM system.events.

D · The sampling profiler

Poor man's flamegraph, in SQL

SET allow_introspection_functions = 1;

SELECT sum(duration_ms) FROM (
    SELECT user_id, count(), avg(duration_ms) AS duration_ms
    FROM lab.events GROUP BY user_id
) SETTINGS query_profiler_real_time_period_ns = 1000000;  -- sample every 1ms

SELECT
    count() AS samples,
    arrayStringConcat(arrayMap(x -> demangle(addressToSymbol(x)), trace), '\n') AS stack
FROM system.trace_log
WHERE event_time > now() - INTERVAL 2 MINUTE AND trace_type = 'Real'
GROUP BY trace
ORDER BY samples DESC
LIMIT 3 FORMAT Vertical;

You are reading the C++ call stacks of your own query. Where do samples land — aggregation? decompression? merge-sort? That tells you which sub-system to investigate.

E · See the query plan

Three EXPLAINs, three angles

EXPLAIN typeWhat it shows
EXPLAIN PLAN actions = 1Logical plan — operators, expressions, projections.
EXPLAIN PIPELINEActual processor graph with thread fan-out (x4, x8...). Verifies max_threads and in-order optimizations.
EXPLAIN ESTIMATEPredicted parts/rows/marks to read, without running anything.
EXPLAIN indexes = 1Per-index granule pruning. Use this to verify a skip index is working.
EXPLAIN SYNTAXThe post-optimizer rewritten query (with PREWHERE moved in, etc.).
F · Gotchas

What experts know

Tool system.events lives next to system.query_log. It records counters with names and descriptions for every ProfileEvent ClickHouse tracks — your decoder ring when ProfileEvents['SomeCounterName'] gives a number you don't recognize.
Pattern Diff ProfileEvents between two runs to find the difference. Same query, two different SETTINGS, two different ProfileEvents maps — the keys that change are where the work went.
Trap The sampling profiler is GLOBAL. Set query_profiler_real_time_period_ns on the single query, not as a session/profile default — otherwise system.trace_log fills up fast.
