SELECT FINAL on a sharded table is silently wrong.

ReplacingMergeTree dedups within a single replica's parts — it does not dedup across shards. Sharded FINAL ships wrong numbers to dashboards and nobody notices until reconciliation. The fix is the argMax pattern from exercise 13, which becomes mandatory in a cluster.

0 · The trap

Why FINAL works on one node and breaks on two

On a single node, FINAL reads all parts of a table, merge-sorts by the ORDER BY key, and keeps the row with the highest version per key. Slow but correct.

On a sharded cluster, the same key can have one version on shard A and a different version on shard B — because they're two separate physical tables. SELECT … FINAL FROM dist_table sends FINAL to each shard. Each shard's FINAL only sees its own parts. The cross-shard duplicate survives. The query returns both rows.

Worse than slow — silently incorrect. Dashboards built on FINAL across shards ship wrong numbers without errors. The fix is to dedup at the initiator, with argMax.

1 · Mental model
  user 42 versions over time:
                   ┌─ (42, 'pro',  v=2) lands on shard 2
                   │
       writes ────►┤
                   │
                   └─ (42, 'free', v=1) lands on shard 1

  SELECT * FROM user_state_dist FINAL WHERE user_id = 42

  Distributed sends FINAL to each shard ──►
      shard 1:  FINAL on its own parts → returns (42, 'free', 1)
      shard 2:  FINAL on its own parts → returns (42, 'pro',  2)

  Initiator unions:
      (42, 'free', 1)  ◄── duplicate that FINAL did NOT remove
      (42, 'pro',  2)

  Result: TWO rows for the same user. Wrong.
2 · Reproduce the bug

Set up the broken case on purpose

Step 1Sharded ReplacingMergeTree.
CREATE TABLE lab.user_state_local ON CLUSTER cluster_2s1r
(
    user_id    UInt32,
    plan       LowCardinality(String),
    updated_at DateTime,
    version    UInt64
)
ENGINE = ReplacingMergeTree(version)
ORDER BY user_id;

CREATE TABLE lab.user_state_dist ON CLUSTER cluster_2s1r AS lab.user_state_local
ENGINE = Distributed('cluster_2s1r', 'lab', 'user_state_local', cityHash64(user_id));
Step 2Force one user onto both shards.

Insert directly into local tables to bypass the sharding key:

# On ch-1:
make sql-1
INSERT INTO lab.user_state_local VALUES (42, 'free', now() - 100, 1);
# On ch-2:
make sql-2
INSERT INTO lab.user_state_local VALUES (42, 'pro', now(), 2);
Step 3Run the naive FINAL.
SELECT user_id, plan, version
FROM lab.user_state_dist FINAL
WHERE user_id = 42;
Wrong answer Returns BOTH rows. FINAL on Distributed only applies FINAL to each shard's slice. Each shard has exactly one row, so "nothing to dedup". The cross-shard duplicate survives.
3 · The fix — argMax

Dedup at the initiator

SELECT user_id,
       argMax(plan, version) AS plan,
       max(version)          AS version
FROM lab.user_state_dist
WHERE user_id = 42
GROUP BY user_id;

One row. argMax(plan, version) returns the plan value from the row with the highest version — across the WHOLE result, regardless of which shard it came from. Works on Replicated AND Distributed, no FINAL needed.

The full "current state of every user" query

SELECT plan, count() AS users
FROM (
    SELECT user_id, argMax(plan, version) AS plan
    FROM lab.user_state_dist
    GROUP BY user_id
)
GROUP BY plan;

This is the production pattern. Faster than FINAL on a single node, and on a cluster it's the only correct approach.

4 · The high-QPS variant — pre-deduped MV

Move the dedup work to ingest time

For dashboards hit thousands of times per second, even argMax over a Distributed query is overhead. Maintain a "current state" target with an AggregatingMergeTree that argMax-merges on insert; dashboard reads the target.

CREATE TABLE lab.user_state_current_local ON CLUSTER cluster_2s1r
(
    user_id UInt32,
    plan    AggregateFunction(argMax, LowCardinality(String), UInt64),
    version SimpleAggregateFunction(max, UInt64)
)
ENGINE = AggregatingMergeTree
ORDER BY user_id;

CREATE MATERIALIZED VIEW lab.user_state_current_mv ON CLUSTER cluster_2s1r
TO lab.user_state_current_local AS
SELECT
    user_id,
    argMaxState(plan, version) AS plan,
    max(version)               AS version
FROM lab.user_state_local
GROUP BY user_id;

-- Dashboard query (no FINAL, no argMax in user-facing SQL):
CREATE TABLE lab.user_state_current_dist ON CLUSTER cluster_2s1r
AS lab.user_state_current_local
ENGINE = Distributed('cluster_2s1r', 'lab', 'user_state_current_local', user_id);

SELECT user_id, argMaxMerge(plan), max(version)
FROM lab.user_state_current_dist
WHERE user_id = 42
GROUP BY user_id;
5 · The pattern hierarchy

FINAL vs argMax vs pre-deduped MV — by setup

Single nodeSharded cluster
argMaxFastest, always correctFastest, always correct
SELECT FINALCorrect, slower (tunable)SILENTLY WRONG — do not use
Pre-deduped MVFastest for dashboardsBest for high-QPS reads

Rule for cluster work: treat any FINAL in a query against a Distributed table as a correctness bug. Replace with argMax at read time, or with a pre-deduped MV at write time.

6 · Gotchas

What experts know

Trap A "good" sharding key hides this bug. If cityHash64(user_id) always sends user 42 to the same shard, you'll never see the cross-shard duplicate during normal traffic. But re-sharding, manual loads, or producer bugs can produce one — and now you have wrong dashboards.
Trap OPTIMIZE TABLE … FINAL on the Distributed table is a no-op. Distributed has no parts — it's a router. Run OPTIMIZE on the per-shard local tables (ON CLUSTER helps).
Pattern If you must use FINAL on a sharded table, pre-aggregate to ONE shard first. E.g. INSERT SELECT into a single-shard MergeTree, run FINAL there. Slow, but correct. Almost always cheaper to switch to argMax.
Pattern For CDC sinks (exercise 22 pattern 4), the target table is ReplacingMergeTree by (pk, version). Reads MUST use argMax, not FINAL. This is one of the most common cluster-incorrectness bugs in the wild.
