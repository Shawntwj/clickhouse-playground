OLTP in. Analytics out.

The most common real-world integration: app data lives in Postgres, analytics live in ClickHouse. Four escalating patterns — pick the one your latency budget allows. Live query, dictionary cache, refreshable MV, full CDC.

1 · Pattern 1 — Live query

No sync at all

SELECT plan, count()
FROM postgresql('postgres:5432', 'app', 'customers', 'postgres', 'lab')
GROUP BY plan;

Every query hits Postgres. Fine for ad-hoc analysis. Don't put this in a hot dashboard JOIN target.

2 · Pattern 2 — Postgres dictionary

Live dims, cached in RAM

CREATE DICTIONARY lab.customers_dict
(
    customer_id UInt32,
    name        String,
    plan        String,
    country     String
)
PRIMARY KEY customer_id
SOURCE(POSTGRESQL(HOST 'postgres' PORT 5432 DB 'app' TABLE 'customers'
                  USER 'postgres' PASSWORD 'lab'))
LAYOUT(HASHED())
LIFETIME(MIN 60 MAX 120);

-- O(1) in-RAM lookup, auto-refreshed every ~minute:
SELECT dictGet('lab.customers_dict', 'plan', toUInt64(42)) AS plan_of_customer_42;

Update a row in Postgres, wait for LIFETIME (or SYSTEM RELOAD DICTIONARY), query again:

docker exec pg psql -U postgres app -c \
  "UPDATE customers SET plan='enterprise' WHERE customer_id=42"

You just built near-real-time dimension sync with zero pipeline code.

3 · Pattern 3 — Refreshable MV

Cron-free ELT in two CREATEs

SET allow_experimental_refreshable_materialized_view = 1;  -- needed on 24.8

CREATE MATERIALIZED VIEW lab.orders_sync
REFRESH EVERY 1 MINUTE
ENGINE = MergeTree ORDER BY (customer_id, created_at)
AS SELECT
    order_id, customer_id,
    toDecimal64(amount, 2) AS amount,
    created_at
FROM postgresql('postgres:5432', 'app', 'orders', 'postgres', 'lab');

-- Watch it run:
SELECT view, status, last_success_time, next_refresh_time
FROM system.view_refreshes;

Now do analytics Postgres couldn't do cheaply, enriched via the dict:

SELECT
    dictGet('lab.customers_dict', 'plan', toUInt64(customer_id)) AS plan,
    count() AS orders,
    sum(amount) AS revenue
FROM lab.orders_sync
GROUP BY plan;

Right answer for tables up to a few tens of millions of rows where minute-level lag is fine. Full refresh is cheap on this scale.

4 · Pattern 4 — True CDC

When you outgrow refreshable MVs

  Postgres WAL  ──►  Debezium  ──►  Kafka  ──►  Kafka engine + MV (exercise 21!)
                                                  into ReplacingMergeTree(version)

  Deletes/updates become versioned rows.
  Reads dedup with the FINAL-dodging tricks from exercise 13.

MaterializedPostgreSQL engine does this natively but is experimental — know it exists, don't bet prod on it.

CDC is just exercises 21 + 13 composed. You already have every piece.

5 · Gotchas

What experts know

Trap The postgresql() function is not free. Every query opens a Postgres connection. For frequent reads, wrap as a dictionary OR a refreshable MV — never a raw table function in a hot path.
Trap Refreshable MVs do a FULL refresh. No incremental sync. At 100M rows this is wasteful; switch to CDC.
Pattern The dictionary pattern is half of "OLAP companion to OLTP" for most teams. Dimensions in CH dictionaries (auto-refreshed), facts in CH MergeTree (CDC'd via Kafka), Postgres stays for transactions only. Single SQL surface, two engines.
