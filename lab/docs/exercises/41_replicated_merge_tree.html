Replication is one engine swap, and you get insert dedup as a bonus.

Change MergeTree to ReplicatedMergeTree, give it a Keeper path, and your data now copies itself to every replica automatically — plus the engine recognizes identical insert blocks and skips duplicates, which is the cheapest exactly-once you'll ever get.

0 · The point

What ReplicatedMergeTree actually does

Plain MergeTree writes a part to local disk and that's it. ReplicatedMergeTree writes a part locally, then writes a log entry to Keeper describing the part. Every other replica of the same shard reads that log, pulls the part from any replica that has it, and stores it locally. A few seconds later, every replica has the same data.

Free bonus: the same Keeper log tracks INSERT block hashes for ~100 partitions back. Re-submit the same block (e.g. a retry from a flaky producer) and the engine silently no-ops it. This is the "exactly once" most teams need.

1 · Mental model
  INSERT on ch-1:
                            ┌──────────────┐
                            │   ch-keeper  │
                            │              │
                            │  /tables/01/ │
                            │   lab/events │
                            │    /log      │
                            └──┬────────┬──┘
                               │        │
        ┌──────────────────────┘        └──────────────────────┐
        ▼                                                       ▼
   ch-1: writes part_1_1_0 locally,                       ch-2: sees new log entry,
   pushes "I have part_1_1_0" log entry                   downloads part_1_1_0 from ch-1,
   to Keeper                                              writes it locally.

  Replication lag = time between log push and part download. Typically < 1s.
2 · Run it

The exercise

Step 1Create a replicated table on cluster_1s2r.
CREATE TABLE lab.events ON CLUSTER cluster_1s2r
(
    event_time  DateTime,
    user_id     UInt32,
    site_id     UInt16,
    country     LowCardinality(String),
    url         LowCardinality(String),
    duration_ms UInt16
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/lab/events',   -- Keeper path (same for all replicas)
    '{replica}'                                 -- per-node identifier (ch-1 / ch-2)
)
ORDER BY (site_id, event_time);

Both nodes resolve {shard} to 01 (same shard = same Keeper path), and {replica} to their own name. Each registers itself under /clickhouse/tables/01/lab/events/replicas/.

Step 2Insert on ch-1, query on ch-2.

Run on ch-1 (make sql-1):

INSERT INTO lab.events
SELECT now() - toIntervalSecond(rand() % 3600),
       rand() % 1000000, rand() % 500,
       ['US','DE','IN'][1 + rand() % 3],
       ['/home','/cart'][1 + rand() % 2],
       rand() % 5000
FROM numbers(100000);

Then on ch-2 (make sql-2):

SELECT count() FROM lab.events;

Expect 100000. Replication is typically sub-second on this local cluster.

Step 3Watch replication state.
SELECT table, replica_name, is_leader,
       absolute_delay, queue_size, log_pointer
FROM system.replicas
WHERE database = 'lab' AND table = 'events';
ColumnWhat it means
queue_sizeLog entries this replica hasn't pulled yet. > 0 climbing = falling behind.
absolute_delaySeconds behind the latest log entry. The metric to alert on.
log_pointerHighest log entry this replica has processed.
is_leaderIn newer CH versions, all replicas can lead (multi-leader merges).
Step 4Free insert deduplication.
INSERT INTO lab.events
SELECT toDateTime('2026-01-01 00:00:00') + number,
       42, 1, 'US', '/home', 100
FROM numbers(10);

Run this twice. Then check:

SELECT count() FROM lab.events WHERE site_id = 1 AND user_id = 42;

Expect 10, not 20. Keeper hashed the block on the first INSERT and stored that hash in its dedup window. The second identical INSERT matches the hash and is silently skipped. Dedup window: insert_deduplication_window entries per partition (default 100).

Step 5Force-catch-up after partition.
SYSTEM SYNC REPLICA lab.events;

Blocks until this replica has processed every log entry. Useful in CI and after manual intervention.

4 · Gotchas

What experts know

Trap Same Keeper path on two different tables = corruption. Each ReplicatedMergeTree table needs its OWN ZK path. Macros in {shard}/{database}/{table} help — e.g. '/clickhouse/tables/{shard}/{database}/{table}'.
Trap Insert dedup is per-block-hash, not per-row. Reorder the same rows in two inserts and they're different blocks, no dedup. Use deterministic block construction if you rely on this.
Trap internal_replication = true matters for Distributed. Without it (or set to false), Distributed will write a copy to EVERY replica directly — duplicating data because ReplicatedMergeTree was about to do that anyway. With true, Distributed writes to one replica and lets the engine replicate. This is set in clusters.xml, not the table.
Pattern SHARED MergeTree is the Cloud-only engine that replaces both Replicated and Distributed by storing parts in object storage with shared metadata. OSS doesn't have it. The OSS pattern (Replicated + Distributed) is what every self-hosted deployment runs.
