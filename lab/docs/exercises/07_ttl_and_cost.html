The fixed-box doctrine.

Autoscaling cloud bills exist because raw data grows forever, scans grow forever, and the cluster grows with them. The self-hosted answer: raw data is a short-lived buffer, rollups are the long-term product, dashboards read rollups behind a query cache. One well-sized box has a known worst case — which is the thing autoscaling charges you to avoid knowing.

0 · The point

The autoscaling trap, in one diagram

Without TTL:
  raw data ──► grows forever ──► dashboards scan more ──► CPU/IO peaks ──► autoscale up ──► $$$

With TTL + rollups:
              hot, small, fast
  raw events ───► TTL 7 days, recompress at 1 day
       │
       └──MVs──► minute rollup  ─ TTL 13 months   ─┐
                hour rollup    ─ TTL 5 years      ├──► dashboards read THIS
                day rollup     ─ TTL forever      ─┘
                                                       constant cost as traffic grows

The math (from this lab): 20M events/day × ~20 bytes compressed = ~400 MB/day raw. 7-day retention = ~3 GB. 1-minute rollup is a few MB/day. A 4–8 GB box handles this with the 4G memory cap in docker-compose.yml.

1 · Run it

The exercise

Step 1Set the basic TTLs.
-- Raw data: keep 7 days, then drop.
ALTER TABLE lab.firehose MODIFY TTL event_time + INTERVAL 7 DAY;

-- Rollup: keep 13 months.
ALTER TABLE lab.events_1m MODIFY TTL minute + INTERVAL 13 MONTH;
Step 2Recompress old data instead of dropping.
ALTER TABLE lab.firehose MODIFY TTL
    event_time + INTERVAL 1 DAY RECOMPRESS CODEC(ZSTD(6)),
    event_time + INTERVAL 7 DAY DELETE;

Recent data lives under fast/light LZ4. After 1 day, parts get rewritten with heavier ZSTD(6) — slower decompress but smaller on disk. After 7 days, deleted. Two TTL clauses, one table.

Step 3Column-level TTL — drop heavy columns first.
ALTER TABLE lab.firehose MODIFY COLUMN url
    LowCardinality(String) TTL event_time + INTERVAL 2 DAY;

Keep the row, but drop the heaviest column after 2 days. URL becomes NULL/empty; everything else (counts, latencies) stays queryable.

Step 4Tiered storage (sketch — needs storage policy config).
-- Production pattern: hot data on NVMe, cold on S3.
ALTER TABLE lab.firehose MODIFY TTL
    event_time + INTERVAL 3 DAY TO VOLUME 'cold';

Requires a storage_policy with two volumes (hot/cold) in config.xml. Once configured, parts older than 3 days physically move to S3-backed cold storage — queries still work, just slower. Routinely replaces autoscaling clusters for dashboard workloads.

Step 5Force TTL evaluation now.
OPTIMIZE TABLE lab.firehose FINAL;

-- Verify the oldest data dropped:
SELECT table, min(min_date) AS oldest, max(max_date) AS newest, sum(rows) AS rows
FROM system.parts
WHERE database = 'lab' AND active
GROUP BY table;
2 · The doctrine

The four-line memorization for keeping a fixed box healthy

  1. Ingestion path gets reserved capacity (threads, memory). It must never compete with reads. → ex. 14
  2. Every human/service gets a profile with memory + time + thread caps. One analyst can't OOM the box.
  3. Dashboards read rollups behind the query cache. 20 Grafana users × 10 s refresh = 1 real query per cache TTL, not 120.
  4. Raw data has a TTL. Disks fill on schedule, not by surprise.

With these four, your worst case is known. That's the thing autoscaling charges you to avoid knowing.

3 · Gotchas

What experts know

Trap TTL is evaluated on merge, not on schedule. A table with few writes may keep dead rows for a long time. OPTIMIZE … FINAL on the partition forces it, but is expensive on huge tables — schedule a per-partition optimize for old data.
Trap TTL on a column with a DEFAULT silently zeros out values, doesn't remove the column. The storage shrinks only modestly. Use row-level TTL for actual size reduction; column TTL is for "I don't care about this data anymore" UX.
Pattern TTL … GROUP BY aggregates rows instead of deleting them — built-in tiered rollup without a separate MV. Use sparingly; one MV chain is usually clearer.
