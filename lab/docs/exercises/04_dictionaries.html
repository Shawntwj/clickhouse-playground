Stop JOINing your dimensions.

A ClickHouse JOIN builds the right side in memory per query. A dictionary loads the dimension table into RAM once, refreshes on a schedule, and turns enrichment into an O(1) dictGet() call. For small slowly-changing tables (sites, customers, geo, feature flags) this is several times faster and uses less memory.

0 · The point

Why JOIN keeps disappointing you

Every JOIN rebuilds the hash table for the right side every single query. With a 500-row dimension that's fine in isolation — but on a busy dashboard with 50 panels each filtering by tier or country, you've now hashed the same 500 rows 50 times. Dictionaries hash once, at load time, then live in RAM until LIFETIME expires.

Mental shift: stop treating dimensions as tables. Treat them as functions you call from the fact table.

1 · Mental model

JOIN vs dictGet, mechanically

JOIN — every query pays

  query 1:  read lab.sites → hash table in RAM → probe 20M rows
  query 2:  read lab.sites → hash table in RAM → probe 20M rows
  query 3:  read lab.sites → hash table in RAM → probe 20M rows
            ^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^
            disk + parse     allocate every time


dictGet — load once, lookups are function calls

  load (once):  read lab.sites → hash into dictionary memory
                LIFETIME timer running...

  query 1:  20M rows × dictGet('sites_dict', 'tier', site_id)  ← O(1)
  query 2:  20M rows × dictGet('sites_dict', 'tier', site_id)  ← O(1)
  query 3:  20M rows × dictGet('sites_dict', 'tier', site_id)  ← O(1)

  refresh (background):  on LIFETIME expiry, ClickHouse re-polls source
2 · Run it

The exercise

Step 1Build a tiny dimension table.
CREATE TABLE lab.sites
(
    site_id UInt16,
    name    String,
    tier    LowCardinality(String),
    owner   String
)
ENGINE = MergeTree ORDER BY site_id;

INSERT INTO lab.sites
SELECT
    number                                            AS site_id,
    concat('site_', toString(number))                 AS name,
    ['free','pro','enterprise'][1 + number % 3]       AS tier,
    concat('team_', toString(number % 20))            AS owner
FROM numbers(500);
Step 2Wrap it as a dictionary.
CREATE DICTIONARY lab.sites_dict
(
    site_id UInt16,
    name    String,
    tier    String,
    owner   String
)
PRIMARY KEY site_id
SOURCE(CLICKHOUSE(DB 'lab' TABLE 'sites' USER 'admin' PASSWORD 'admin'))
LAYOUT(HASHED())          -- all in RAM, hashed by key. CACHE() for huge sources.
LIFETIME(MIN 60 MAX 120); -- re-poll every 60-120s → near-real-time dim updates
Step 3Benchmark — JOIN vs dictGet on 20M rows.
-- 1) Classic JOIN
SELECT s.tier, count() AS events, quantile(0.95)(duration_ms) AS p95
FROM lab.events e
INNER JOIN lab.sites s ON e.site_id = s.site_id
GROUP BY s.tier;

-- 2) dictGet
SELECT dictGet('lab.sites_dict', 'tier', toUInt64(site_id)) AS tier,
       count() AS events,
       quantile(0.95)(duration_ms) AS p95
FROM lab.events
GROUP BY tier;

Expect: dictGet typically 3–10× faster on this dataset, and uses less memory. Confirm with: 

SELECT query_duration_ms, formatReadableSize(memory_usage) AS mem,
       substring(query, 1, 60) AS q
FROM system.query_log
WHERE type = 'QueryFinish' AND query ILIKE '%tier%' AND query_kind = 'Select'
ORDER BY event_time DESC LIMIT 4;
Step 4Watch auto-refresh.

Update a row in the source table and wait ~2 minutes (or force it):

INSERT INTO lab.sites VALUES (1, 'site_1', 'enterprise', 'team_1');

-- force immediate reload:
SYSTEM RELOAD DICTIONARY lab.sites_dict;

SELECT dictGet('lab.sites_dict', 'tier', toUInt64(1));   -- 'enterprise'

The dictionary tracks the source. You just built near-real-time dimension sync with one DDL statement and zero pipeline code.

3 · Layout choice

Which layout for which source

LayoutBest forTrade-off
HASHEDSingle key, fits in RAM (default for small dims)Whole table in RAM; reload re-reads everything.
COMPLEX_KEY_HASHEDMulti-column key (e.g. date+area+calendar)Pass key as tuple: (date, 'NSW', 'AEMO').
FLATTiny dense integer keys (e.g. 0..1000)Fastest, but key space must be small.
CACHE / COMPLEX_KEY_CACHESource too big for RAM; only some keys hotLRU cache, misses hit source — slower under pressure.
RANGE_HASHEDRange-keyed lookups (history of prices, etc.)Specialty layout, niche use cases.
4 · Gotchas

What experts know

Trap The dictionary key type is fixed at UInt64 for simple keys. If your source has UInt16 site_id, you must toUInt64(site_id) when calling dictGet. Type mismatch = silent zero results.
Trap Use dictGetOrDefault, not dictGet, in any analytical query. Missing keys return zero/empty silently with dictGet; dictGetOrDefault lets you supply a sentinel and inspect misses later.
Pattern External sources work the same. Postgres, MySQL, MongoDB, Redis, an HTTP endpoint — anything ClickHouse can read. See exercise 22 for a Postgres-sourced dict.
Settings LIFETIME(MIN 0 MAX 0) = never auto-refresh; you reload manually with SYSTEM RELOAD DICTIONARY. Useful when the source rarely changes and you want determinism.
