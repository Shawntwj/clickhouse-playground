The MV is an INSERT trigger, not a cached query.

Pay the aggregation cost once at write time, then dashboards read thousands of rolled-up rows instead of millions of raw ones. Async inserts → MV → tiny rollup reads is the entire near-real-time architecture; no streaming framework required.

0 · The point

Cached queries vs INSERT triggers

In Postgres, a "materialized view" caches a query result that you refresh manually. In ClickHouse, a materialized view is something different: an INSERT trigger that transforms each inserted block and routes it into a target table. The target table is what you query.

Net effect: every row written to the raw table also lands, pre-aggregated, in the rollup table. Latency from "row written" to "rollup updated" is sub-second.

1 · Mental model

The architecture

                       (async inserts buffer here)
                                   │
                                   ▼
  INSERT block ──►  lab.firehose      raw events, TTL 7 days
                       │
                       └──MV (the trigger)──►  lab.events_1m   AggregatingMergeTree
                                                  ▲              kept 13 months
                                                  │
                                              Grafana reads HERE, never raw

  The MV runs DURING the insert, against the BLOCK being written.
  It does NOT see existing rows — only future ones.
  → Backfill historical aggregates manually after creating the MV.
2 · Run it

The exercise

Step 1Create the target (the rollup table).
CREATE TABLE lab.events_1m
(
    minute      DateTime,
    site_id     UInt16,
    events      UInt64,
    duration_q  AggregateFunction(quantile(0.95), UInt16)
)
ENGINE = AggregatingMergeTree
ORDER BY (site_id, minute);

AggregatingMergeTree merges rows with the same ORDER BY key by combining their aggregate-state columns. AggregateFunction(quantile(0.95), UInt16) is the storage type for a t-digest sketch you'll merge later.

Step 2Create the MV (the trigger).
CREATE MATERIALIZED VIEW lab.events_1m_mv TO lab.events_1m AS
SELECT
    toStartOfMinute(event_time)               AS minute,
    site_id,
    count()                                   AS events,
    quantileState(0.95)(duration_ms)          AS duration_q
FROM lab.firehose
GROUP BY minute, site_id;

Note quantileState — writes the sketch, not the final number. Reads will use quantileMerge to combine sketches.

Step 3Backfill historical aggregates.
INSERT INTO lab.events_1m
SELECT toStartOfMinute(event_time), site_id, count(), quantileState(0.95)(duration_ms)
FROM lab.events
GROUP BY 1, 2;

MVs only see new inserts. To get history into the rollup, you run an explicit aggregation INSERT. Do this after creating the MV so new inserts also flow in.

Step 4Compare reads: raw vs rollup.
-- Raw (scans millions of rows)
SELECT toStartOfMinute(event_time) AS m, count(), quantile(0.95)(duration_ms)
FROM lab.events
WHERE event_time > now() - INTERVAL 6 HOUR
GROUP BY m ORDER BY m;

-- Rollup (scans a few thousand pre-aggregated rows)
SELECT minute, sum(events), quantileMerge(0.95)(duration_q)
FROM lab.events_1m
WHERE minute > now() - INTERVAL 6 HOUR
GROUP BY minute ORDER BY minute;

Order-of-magnitude latency difference, identical answer. The rollup costs essentially nothing per query.

Step 5The feedback loop — see it live.
# terminal 1
make storm-async

# terminal 2 (Grafana)
# Add a panel on lab.events_1m with 5s refresh:
#   SELECT minute AS time, sum(events) AS events
#   FROM lab.events_1m
#   WHERE minute >= $__fromTime GROUP BY minute ORDER BY minute

Inserts appear in the rollup within 1–2 seconds. That is near-real-time analytics: async insert buffer → MV → tiny read.

3 · State combinators

The -State / -Merge dance

Aggregate functions in CH have three flavors. Get this once and the rest is mechanical:

VariantReturnsUse where
quantile(0.95)(x)The numberDirect query against raw data.
quantileState(0.95)(x)The partial sketch (bytes)Inside the MV — what's stored in the target.
quantileMerge(0.95)(state)The number, from sketchesReading from the rollup table.

Same pattern for uniqState/Merge, avgState/Merge, etc. For pure counts/sums, SummingMergeTree is simpler — no state combinators needed.

4 · Gotchas

What experts know

Trap MV runs INSIDE the insert. A heavy MV slows ingestion for everyone. Keep transforms lean. If the math is expensive, chain MVs (raw → 1min → 1h → 1d) rather than one monster MV.
Trap MVs do NOT see existing data. Backfill is always a separate INSERT … SELECT … FROM raw GROUP BY …. Forget this and your dashboard mysteriously has only the last hour of data.
Pattern Multiple MVs on one source = fan-out. One lab.firehose can feed a 1-minute rollup, a country rollup, AND a kafka-style downstream — three CREATE statements. This is what people pay streaming frameworks for.
Trap If the MV's SELECT fails on a block, that block's ingestion fails too. Be defensive with parseDateTimeBestEffort, toFloatOrZero, etc. on data of uncertain shape.
