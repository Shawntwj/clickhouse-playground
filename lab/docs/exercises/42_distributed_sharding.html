The Distributed engine is a router, not a storage engine.

A Distributed table points at per-shard storage tables on a cluster. Writes route by a sharding key; reads fan out and merge. The same data model that scales a single laptop also scales to a hundred nodes — same SQL, same engines, just more shards.

File · lab/sql/42_distributed_sharding.sql Reading · ~14 min Level · Cluster Prereq · exercise 40
0 · The point

Two tables, one logical view

Sharding is conceptually simple: split a big table by a key (cityHash64(user_id) % N), put each slice on a different node. The Distributed engine glues the slices back together — your SELECT looks like a single table, but underneath it fans out to every shard, runs the query locally on each, and merges the partial results.

The mental shift: you write to the Distributed table; data lands in local tables on the shards. You read from the Distributed table; the engine does the scatter-gather.

2 · Run it

Build the two-layer setup

Step 1Per-shard storage table.
CREATE TABLE lab.events_local ON CLUSTER cluster_2s1r
(
    event_time  DateTime,
    user_id     UInt32,
    site_id     UInt16,
    country     LowCardinality(String),
    url         LowCardinality(String),
    duration_ms UInt16
)
ENGINE = MergeTree
ORDER BY (site_id, event_time);

Plain MergeTree — no replication on cluster_2s1r (it's 2 shards × 1 replica). For an HA-AND-sharded production cluster, swap MergeTree for ReplicatedMergeTree and use a cluster with N shards × M replicas.

Step 2Distributed table on top.
CREATE TABLE lab.events_dist ON CLUSTER cluster_2s1r AS lab.events_local
ENGINE = Distributed(
    'cluster_2s1r',     -- cluster name from clusters.xml
    'lab',              -- target DB on each shard
    'events_local',     -- target table
    cityHash64(user_id) -- sharding key
);

The sharding key is optional but recommended. Without it, INSERTs go round-robin (or to the local shard). A good key produces uniform distribution and co-locates related rows.

Step 3Insert and verify distribution.
INSERT INTO lab.events_dist
SELECT now() - toIntervalSecond(rand() % 3600),
       rand() % 1000000, rand() % 500,
       ['US','DE','IN'][1 + rand() % 3],
       ['/home','/cart'][1 + rand() % 2],
       rand() % 5000
FROM numbers(1000000);

-- Where did the data actually land?
SELECT hostName() AS host, count() AS rows_on_this_node
FROM clusterAllReplicas('cluster_2s1r', lab.events_local)
GROUP BY host;

Roughly 500k on ch-1, 500k on ch-2. Hash distribution is random but uniform for a uniformly distributed key. Skewed keys (e.g. tenant_id where one tenant has 90% of traffic) produce skewed shards.

Step 4Fan-out aggregation.
SELECT count(), uniq(user_id) FROM lab.events_dist;

Each shard runs count() locally. The initiator sums the two partials. uniq() ships the HLL state across the wire, not raw values — most aggregations were designed for this and are mergeable. Plain count(DISTINCT user_id) is NOT mergeable across shards correctly without the HLL trick — that's why CH ships uniq and friends.

3 · Cross-shard JOIN — the trap and three fixes

A naive JOIN on a Distributed table sends the RIGHT side to each shard separately. If the right side itself lives on Distributed, each shard sees only its own slice — and rows that should join across shards silently drop. Three options:

ApproachWhen
1. GLOBAL JOIN / GLOBAL IN
GLOBAL ANY INNER JOIN		Initiator collects right side once and broadcasts to every shard. Right side small.
2. Dictionary dictGetLoad dimension into RAM on every node (ON CLUSTER). The default cluster pattern. Exercise 04 was the foundation; in a cluster the win is even larger because JOIN is even more fraught.
3. distributed_product_modeSetting: deny errors if the JOIN risks wrong answers; local assumes you've co-located keys; global auto-promotes to GLOBAL JOIN.
 
-- GLOBAL ANY INNER JOIN example: small right side, broadcast once.
SELECT count() FROM lab.events_dist e
GLOBAL ANY INNER JOIN (SELECT 1 AS site_id, 'tier_a' AS tier) s
USING site_id;
4 · Settings worth memorizing
SettingWhat it does
insert_distributed_sync = 1Wait for ack from each shard before returning. Slower, safer. Default async.
prefer_localhost_replica = 1Cut a network hop when the initiator is also a replica.
max_parallel_replicas = NSplit a single query across N replicas of the same shard for parallelism.
distributed_aggregation_memory_efficient = 1Stream partial aggregates back rather than buffering — lower memory on the initiator.
5 · The _shard_num virtual column
SELECT shard_num, count() AS rows
FROM (
    SELECT _shard_num AS shard_num
    FROM clusterAllReplicas('cluster_2s1r', lab.events_local)
)
GROUP BY shard_num ORDER BY shard_num;

_shard_num is a virtual column on clusterAllReplicas() and Distributed reads. Use it to verify sharding distribution and find skew. Huge gap between shards = bad sharding key or hot tenant.

6 · Gotchas

What experts know

Trap You can't change the sharding key without re-sharding. Like ORDER BY, it's a design decision. Pick a key that uniformly distributes AND keeps related rows together (e.g. all of one user's events on the same shard for cheap GROUP BY user_id).
Trap INSERT INTO Distributed is async by default. Rows go to a spool directory on the initiator, then forward in the background. A node crash can lose unsynced rows. insert_distributed_sync=1 trades latency for durability.
Trap internal_replication=true in clusters.xml is mandatory with ReplicatedMergeTree. Without it, Distributed will write to EVERY replica directly, duplicating data the engine was about to replicate anyway. The lab's config has it right; check it when copy-pasting elsewhere.
Pattern Most teams over-shard early. ClickHouse vertically scales obscenely well — a single 32-core/128GB box handles billions of rows. Run on one big node first; shard only when you've hit a real wall.
