clickhouse-playground / lab / exercises / 21 · kafka_pipeline

A streaming pipeline in three CREATE statements.

Kafka engine table = the consumer. MV = the pump that pulls + transforms + writes. MergeTree = storage. No separate worker process, no exactly-once orchestration framework, no library to vendor. Most companies' "streaming pipeline" is exactly these three DDLs.

0 · The point

The three-piece anatomy

  Kafka topic ──►  Kafka ENGINE table ──►  MV (the pump) ──►  MergeTree
                   (a consumer,             transforms +       (storage)
                    not storage)            validates

  The Kafka table holds nothing; reading from it consumes messages.
  The MV is what continuously pulls and writes. No MV = no ingestion.

The MV pumps Kafka messages into the SAME storage table that other exercises use. One lab.firehose, many ingestion paths.

1 · Run it

Spin up the pipeline

Step 0Make sure integrations are up.
make up-integrations

# Create the topic:
docker exec redpanda rpk topic create events -p 3
Step 1The consumer.
CREATE TABLE lab.kafka_events
(
    ts          String,            -- arrive loose, parse in the MV
    user_id     UInt32,
    site_id     UInt16,
    country     String,
    url         String,
    duration_ms UInt16
)
ENGINE = Kafka
SETTINGS kafka_broker_list = 'redpanda:9092',
         kafka_topic_list = 'events',
         kafka_group_name = 'clickhouse',
         kafka_format = 'JSONEachRow',
         kafka_num_consumers = 1;
Step 2The pump.
CREATE MATERIALIZED VIEW lab.kafka_pump TO lab.firehose AS
SELECT
    parseDateTimeBestEffort(ts) AS event_time,
    user_id, site_id, country, url, duration_ms
FROM lab.kafka_events;

The MV does the transformation — parse the loose ts string into a real DateTime, route into the unified storage table. Add WHERE clauses for filtering, dictGet for enrichment, anything SQL can express.

Step 3Produce!
make kafka-storm

Watch lab.firehose grow and Grafana panels move: 

SELECT count(), max(event_time) FROM lab.firehose;
2 · Operations you must know

The four things that come up in prod

Consumer lag / errors

SELECT database, table, num_messages_read, last_exception_time, exceptions.text
FROM system.kafka_consumers FORMAT Vertical;

Bad message handling

Don't let one poison message stall the stream. Set kafka_handle_error_mode = 'stream' on the Kafka table — it exposes _error and _raw_message virtual columns. Route failures to a dead-letter table with a second MV.

Pause / resume

DETACH TABLE lab.kafka_events;
ATTACH TABLE lab.kafka_events;

Offsets live in Kafka under the consumer group, so this is safe — no message loss.

Replay from scratch

docker exec redpanda rpk group delete clickhouse
# Then DETACH/ATTACH the Kafka table. Consumer starts from earliest.
3 · Why this beats a custom consumer

The MV is a SQL transformation layer at ingestion time:

  • Cast/validate types
  • Enrich via dictGet (no separate Kafka Streams join)
  • Filter junk
  • Fan out to multiple targets (just add more MVs reading the same Kafka table — different consumer groups)

All of this in SQL, all running inside the database that's serving your dashboards. Zero extra processes to deploy.

4 · Gotchas

What experts know

Trap The MV defines what data lands. If the MV's SELECT crashes on a row, that row is consumed and lost. Use defensive parsing (parseDateTimeBestEffortOrNull) and route failures to a dead-letter table.
Trap Scaling consumers across replicas needs kafka_num_consumers tuned per shard. One ClickHouse node × N consumers = parallelism on that node. Multiple nodes need separate consumer groups OR proper partition assignment.
Pattern Two MVs reading the same Kafka table = fan-out with different transformations. One can land raw, another can pre-aggregate, both share the offset. Each MV gets its own consumer group.
Trap Schema evolution is manual. Add a column to the Kafka table → restart consumers (DETACH/ATTACH). Producer-side schema registry is your friend at scale.
