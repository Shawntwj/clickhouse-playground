system.* tables are per-node. clusterAllReplicas fans them out.

Every ClickHouse server has its own query_log, parts, replicas. To answer "is anything slow / behind / broken across the fleet?" you wrap the per-node system table in clusterAllReplicas() and the query runs everywhere at once. This is the pattern your dashboards should be built on.

0 · The point

Why per-node observability isn't enough

On a single node, SELECT * FROM system.query_log tells you everything. On a 6-node cluster, that same query tells you about one node — and any one node could be the one straggling. You either ssh-and-query each, or you wrap the call in clusterAllReplicas('cluster_name', system.query_log) and the query fans out automatically.

The shift: stop typing system.X in cluster work. Start typing clusterAllReplicas('cluster_name', system.X). That single habit fixes most "we can't see what's happening in prod" complaints.

A · Fleet-wide query_log

The first dashboard you should build

SELECT
    hostName()           AS host,
    count()              AS queries,
    round(avg(query_duration_ms)) AS avg_ms,
    max(query_duration_ms)        AS max_ms
FROM clusterAllReplicas('cluster_1s2r', system.query_log)
WHERE event_date = today() AND type = 'QueryFinish'
GROUP BY host
ORDER BY host;

One row per node. Lets you spot a single slow replica without ssh-ing in. If avg_ms is similar across hosts but max_ms is high on one — that host had a runaway query. Drill into it with a WHERE hostName() = '…' filter.

B · Distributed queries

How to find the straggling shard

A Distributed query writes ONE row on the initiator and ONE row on each shard that participated. They share initial_query_id. Use this to find queries whose total time was dominated by one slow shard: 

SELECT
    initial_query_id,
    countIf(is_initial_query = 1) AS initiator_rows,
    countIf(is_initial_query = 0) AS shard_rows,
    max(query_duration_ms)        AS slowest_shard_ms,
    sum(read_rows)                AS total_rows_read
FROM clusterAllReplicas('cluster_2s1r', system.query_log)
WHERE event_date = today() AND type = 'QueryFinish'
GROUP BY initial_query_id
HAVING shard_rows > 0
ORDER BY slowest_shard_ms DESC
LIMIT 10;

High slowest_shard_ms with low average = one shard is the straggler. That's where you focus the investigation.

C · Replication health

The query that should be on a 1-minute schedule

SELECT
    hostName()        AS host,
    database, table,
    queue_size, absolute_delay,
    if(absolute_delay > 60, 'BEHIND', 'ok') AS status
FROM clusterAllReplicas('cluster_1s2r', system.replicas)
WHERE database = 'lab'
ORDER BY absolute_delay DESC;

absolute_delay > 60 is usually action-worthy: merge starvation, slow disk, or a network partition with Keeper. Alert on this; don't wait for users to notice stale data.

D · Parts distribution

Are the replicas actually in sync?

SELECT
    hostName()                AS host,
    database, table,
    count()                   AS active_parts,
    sum(rows)                 AS rows,
    formatReadableSize(sum(bytes_on_disk)) AS size
FROM clusterAllReplicas('cluster_1s2r', system.parts)
WHERE active AND database = 'lab'
GROUP BY host, database, table
ORDER BY host, table;

For ReplicatedMergeTree both replicas should be near-identical. A big mismatch in rows = one replica is lagging. Correlate with section C — usually the same node.

E · Distributed ingest queue

Where async-inserted-to-Distributed rows go to wait

SELECT
    hostName()  AS host,
    database, table,
    is_blocked, error_count, data_files,
    formatReadableSize(data_compressed_bytes) AS pending
FROM clusterAllReplicas('cluster_2s1r', system.distributed_queue);

When you INSERT INTO a Distributed table, rows first write to a spool directory on the initiator, then forward to the destination shard. error_count climbing = a destination shard is rejecting writes. is_blocked = queue paused (manual or after too many errors).

F · The third-cluster pattern

For long-term retention, ship logs centrally

clusterAllReplicas() is fine for ad-hoc queries and dashboards on a healthy cluster. For long-term retention (analyze last 90 days of query patterns), don't keep system.query_log forever on every prod node — ship it. 

  prod cluster                 obs cluster
  ┌──────────┐                  ┌──────────┐
  │   ch-1   │  ── MV ──►       │          │
  │          │            ┌────►│  Distributed table │
  │ query_log│            │     │  over 1+ shards     │
  └──────────┘            │     │                     │
  ┌──────────┐            │     │  retention: 90 days │
  │   ch-2   │  ── MV ──► │     │  partition: monthly │
  │          │            │     └──────────┘
  │ query_log│            │
  └──────────┘            │     The MV transforms system.query_log → enriched
                                row → Distributed.insert → land on obs cluster.

Sketch on each prod node: 

CREATE MATERIALIZED VIEW obs_pump TO obs_dist AS
SELECT hostName() AS host, * FROM system.query_log;

obs_dist points at a Distributed table on the obs cluster. This is what every team eventually builds. Perfect demo of exercises 05 (MV) + 21 (Kafka, optional) + 42 (Distributed) composed.

G · Gotchas

What experts know

Trap clusterAllReplicas queries every replica. On a sharded cluster with replicas, that's 2× the work for the same data. Prefer cluster() if you want one replica per shard. Use clusterAllReplicas specifically when you need per-replica state (e.g. checking lag).
Trap system.query_log has its own TTL. Default keeps a few weeks. For longer history you need the third-cluster pattern OR a longer TTL configured in config.d/query_log.xml — which makes the per-node table big and your cluster-wide query slow.
Pattern One Grafana dashboard, one set of cluster queries. If you find yourself copy-pasting FROM system.X into every panel, replace it with FROM clusterAllReplicas('cluster_name', system.X) once and your dashboard becomes fleet-aware in one diff.
