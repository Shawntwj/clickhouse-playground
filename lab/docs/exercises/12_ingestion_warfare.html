How hard can one box swallow?

The ingestion throughput ladder, plus two patterns most teams don't know exist: the Null engine (swallow infinitely, store nothing — MVs still fire) and the Buffer engine (RAM shock absorber for the rare cases async_insert isn't enough).

B · The ceiling test

Synthesize inside the server

INSERT INTO lab.firehose
SELECT now() - toIntervalSecond(rand() % 3600),
       rand() % 1000000, rand() % 500,
       ['US','DE','IN'][1 + rand() % 3],
       ['/home','/cart'][1 + rand() % 2],
       rand() % 5000
FROM numbers_mt(50000000)
SETTINGS max_insert_threads = 4, max_threads = 4;

Note rows/sec in the client output. This is your hardware's limit. Everything slower than this is your pipeline's fault, not ClickHouse's.

SettingWhat it controls
max_insert_threadsParallel part writers (CPU for speed)
min_insert_block_size_rowsBigger blocks = fewer, bigger parts (less merge work)
input_format_parallel_parsingText formats parse on multiple cores
insert_deduplicateFor Replicated tables; set to 0 if you don't need block-hash dedup
C · The Null engine trick

Ingest infinitely, store nothing

ENGINE = Null swallows inserts and discards them — but materialized views attached to it still fire. So: raw stream in, only rollups stored. 

CREATE TABLE lab.blackhole AS lab.firehose ENGINE = Null;

CREATE MATERIALIZED VIEW lab.blackhole_1m_mv TO lab.events_1m AS
SELECT toStartOfMinute(event_time) AS minute, site_id,
       count() AS events, quantileState(0.95)(duration_ms) AS duration_q
FROM lab.blackhole
GROUP BY minute, site_id;

INSERT INTO lab.blackhole
SELECT now(), rand() % 1000000, rand() % 500, 'US', '/home', rand() % 5000
FROM numbers_mt(10000000);

SELECT minute, sum(events) FROM lab.events_1m
WHERE minute >= toStartOfMinute(now()) GROUP BY minute;

10M events ingested, ~500 rows stored. Storage cost: effectively zero. This is the extreme-volume pattern — metrics, ad impressions, IoT — when you only ever need aggregates, never store the raw stream at all.

Variant: Null table + several MVs = one stream fanned out to N rollups. Zero storage, zero pipeline code.

D · The Buffer engine

RAM shock absorber (pre-async-insert era)

CREATE TABLE lab.firehose_buffer AS lab.firehose
ENGINE = Buffer(lab, firehose, 16,
                10, 100,        -- min/max seconds before flush
                10000, 1000000, -- min/max rows
                1000000, 10000000); -- min/max bytes

Writes go to the buffer; RAM chunks flush to lab.firehose when any max threshold hits. SELECTs on the buffer see RAM + disk combined — useful when reads must see writes the same millisecond they arrive.

Trade-offs vs async_insert: a crash loses the buffer, and no PK order in RAM. Modern default is async_insert; reach for Buffer when reads must be instant.

E · The pattern summary

Pick one

SituationPattern
Many tiny producers, normal scaleasync_insert → MergeTree (the default)
Insane volume, aggregates onlyNull table + MVs (store nothing)
Must read instantly + can't batchBuffer engine (RAM shield)
Bulk load / backfillNative format or INSERT SELECT, max_insert_threads up, load per partition so merges stay local
F · Gotchas

What experts know

Trap Buffer engine doesn't survive restarts. A graceful shutdown does flush; a crash doesn't. Async_insert has the same crash semantics — your durability story has to be upstream.
Pattern Null + MV fan-out scales to absurd volumes. Companies pay for streaming frameworks to do less than this single ClickHouse pattern.
Trap RowBinary is much faster than CSV but no schema in the file. Producer and consumer must agree on column order. Mismatches are silent and catastrophic.
