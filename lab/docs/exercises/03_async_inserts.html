The parts war, and how to win it.

Every INSERT creates a new part (a directory on disk). Background merges combine them. Insert faster than merges can keep up and parts explode — eventually you hit Too many parts and ingestion dies. This exercise breaks the system on purpose, then shows the two ways to fix it.

File · lab/sql/03_async_inserts.sql + lab/scripts/insert_storm.sh Reading · ~12 min Level · Fundamentals Prereq · make up
0 · The point

Why "too many parts" is the most famous ClickHouse error

A naive deployment streams individual rows from clients ("just one INSERT per request, what could go wrong"). Each becomes a tiny part. Merges, which are O(rows), can't catch up. parts_to_throw_insert trips. Ingestion stops. 3 a.m. page.

The decision tree: batch on the client if you can. If you can't, async_insert=1 moves the buffering server-side. There is no third option that's not weird.

1 · Mental model

Sync vs async inserts

SYNC (the default, the disaster)

  client 1 ─►─┐
  client 2 ─►─┤  2000 INSERTs ──► 2000 parts ──► merge storm ──► "Too many parts"
  client N ─►─┘

ASYNC (async_insert=1)

  client 1 ─►─┐                  in-memory buffer
  client 2 ─►─┼─►─ server   ─►   [accumulates rows]   ─►  ONE part every ~1s
  client N ─►─┘                      flush on:
                                       • async_insert_busy_timeout_ms
                                       • async_insert_max_data_size

  ack semantics:
    wait_for_async_insert = 1  →  client gets ack AFTER flush  (durable)
    wait_for_async_insert = 0  →  ack immediately              (fast, crash loses buffer)
2 · Run it

Break it, then fix it

Step 1Create the target table.
CREATE TABLE IF NOT EXISTS lab.firehose
(
    event_time  DateTime,
    user_id     UInt32,
    site_id     UInt16,
    country     LowCardinality(String),
    url         LowCardinality(String),
    duration_ms UInt16
)
ENGINE = MergeTree
ORDER BY (site_id, event_time);
Step 2Break it: 2000 sync inserts.
make storm-sync

Open Grafana → Feedback Loop. Watch Active parts climb in a near-straight line. Merges running maxes out — the server is fighting itself. Crank N high enough and you'll see Too many parts (N). Merges are processing significantly slower than inserts. — the canonical error.

Step 3Reset and fix it: same inserts, async.
docker exec clickhouse clickhouse-client -u admin --password admin \
  -q "TRUNCATE TABLE lab.firehose"
make storm-async

Same 2000 inserts. Active parts now stays flat. Async insert flushes / sec ticks at ~1/sec. Roughly 2000× fewer parts, same data ingested.

Step 4Watch the buffer live.
SELECT * FROM system.asynchronous_inserts;

During storm-async you'll see rows in flight, their query hash, and which user. After flush the entry disappears. This table is the source of truth for "are async inserts buffering or stuck?"

3 · The decision tree

Which path is yours?

SituationDo this
You control the clientBatch: 10k–500k rows per INSERT, ≤ ~1 insert/sec/table. Nothing beats it.
Many small producers you don't controlasync_insert = 1. Choose ack semantics next.
Need maximum throughput; can tolerate buffer loss on crashasync_insert=1, wait_for_async_insert=0 (fire-and-forget).
Need durability per writeasync_insert=1, wait_for_async_insert=1 (default). Client acks after flush.
Insane volume, only aggregates matterSkip storing raw entirely — exercise 12 (Null engine + MV).

Key tuning knobs (per-query SETTINGS or in a profile):

async_insert = 1                          -- turn it on
wait_for_async_insert = 1                -- ack AFTER flush (durable, default)
async_insert_busy_timeout_ms = 1000     -- flush every N ms
async_insert_max_data_size = 10485760  -- ...or when buffer hits N bytes
4 · Gotchas

What experts know

Trap async_insert is per-shape. Two inserts with different column orders or different column sets buffer separately. Send identical INSERT shapes from every client.
Trap Server crash with wait_for_async_insert=0 loses the in-RAM buffer. That's the trade. If your producer can re-emit, it's fine. If it can't, use the durable mode or batch on the client.
Pattern async_insert is the budget Kafka. At small-to-medium scale, "Kafka in front of ClickHouse just to buffer writes" is a fully managed cluster's worth of complexity to solve a problem one setting fixes. Reach for Kafka when you need fan-out or replay, not just buffering.
