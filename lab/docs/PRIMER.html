Five facts about the engine.
Everything else is a consequence.

ClickHouse isn't fast because of magic settings. It's fast because of how bytes are laid out on disk — and slow when you fight that layout. Each simulator below is one fact about the engine; each maps to a lab exercise where you prove it on your own box.

FACT 1 · prove it in sql/01 + sql/02

Columns are files

A row database stores each row together, so reading two columns means dragging every column off disk. ClickHouse stores each column as its own compressed file — a query touches only the files it names. Toggle the layout and watch how many bytes this query actually reads:

SELECT country, avg(duration_ms) FROM events GROUP BY country

Consequence: narrow types, LowCardinality, and codecs (exercise 02) multiply this win — smaller files, less I/O, for every query forever. And SELECT * throws the whole advantage away.

FACT 2 · prove it in sql/01 + sql/06 with EXPLAIN indexes=1

The index is sparse — it skips, it never finds

One index entry per granule of 8,192 rows. The index can't locate a row; it can only say "this block of 8,192 can't match — skip it." Skipping only works if matching rows sit together, and what sits together is decided by ORDER BY. Same query, same data, two sort keys:

SELECT quantile(0.95)(duration_ms) FROM events WHERE site_id = 42 AND event_time > now() - 7d

Consequence: ORDER BY is 80% of your performance and is chosen once. Filter columns first, low→high cardinality. When a second query pattern fights the sort key: projections and skip indexes (exercise 06) — extra index structures, same skipping idea.

FACT 3 · prove it with make storm-sync / storm-async · sql/03 + sql/11

Every insert is a part. Merges are the heartbeat.

An INSERT never modifies anything — it writes a brand-new immutable part (a directory). Background merges fold small parts into bigger ones, forever. Insert in tiny pieces faster than merges can fold, and parts pile up until the engine throws Too many parts. Drive it yourself:

Consequence: batch on the client, or let async_insert=1 batch on the server (toggle it above, then spam tiny inserts). Exercise 11 lets you freeze real merges with SYSTEM STOP MERGES and watch the same disease in Grafana. Immutable parts are also why partition DROP is instant and row mutations are slow — design for the former.

FACT 4 · prove it in sql/05 + sql/13 + sql/07

Pay at write time, once — not at read time, forever

A materialized view is an insert trigger: each incoming block is aggregated into a rollup table as it arrives. Dashboards then read thousands of pre-aggregated rows instead of re-scanning millions of raw ones — and the query cache collapses repeated reads to one real query per TTL. This is the entire "real-time without autoscaling" argument, in numbers you choose:

Consequence: dashboards read rollups, never raw. Raw data gets a TTL and becomes a short-lived debugging buffer (exercise 07). Query cost stops depending on traffic — which is precisely the dependency autoscaling charges you for.

FACT 5 · prove it in sql/10 — ProfileEvents, trace_log, EXPLAIN PIPELINE

The engine narrates itself

Every query leaves ~400 counters in system.query_log; the sampling profiler captures its C++ stacks; EXPLAIN predicts its reads before it runs. Mastery is one habit: predict → run → diff the telemetry. A wrong prediction marks the gap in your mental model. Where to look:
