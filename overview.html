And how to use this lab to learn it.

0 · What ClickHouse actually is

A columnar database that turned compression and sparse indexing into a religion.

ClickHouse stores each column in its own compressed file. When you query, it touches only the columns you asked about — not the rows, not the table, just the columns. On top of that it never finds a row directly: it has a sparse primary index that lets it skip blocks of 8192 rows, then reads the rest. That's the whole magic trick, and it's why a single laptop-sized box handles workloads that look like they need a cluster.

The catch is that this only works if you set things up so the engine can skip. Get ORDER BY wrong and it scans everything. Insert one row at a time and merges drown. Read raw data when you should be reading a rollup and you pay for the same scan a million times. This course is the exhaustive list of those skips, and the conditions under which they fire.

Working definition. An expert isn't someone who knows every setting — it's someone who can look at a query and immediately picture which columns get read, which granules get pruned, and which cache gets touched. Get the picture right; the settings follow.
1 · The mental model in 60 seconds

Three truths drive ~90% of all ClickHouse optimization.

If you internalize these three sentences and nothing else, you've got the foundation every later exercise builds on.

TRUTH 1

Columns are files.

Narrow types and good compression mean less I/O, smaller CPU caches, faster everything. A UInt16 beats a UInt64 before any optimization. A LowCardinality(String) shrinks a country column 10×. Codecs (Delta, Gorilla, T64) exploit the shape of your data before ZSTD even runs.

TRUTH 2

The index is sparse.

ClickHouse never finds a row — it skips granules of 8192 rows using the ORDER BY tuple. If your dominant query filters by site_id and you sorted by user_id, the index skips nothing and you scan 20M rows. Get this right and you scan thousands.

TRUTH 3

Every INSERT makes a part.

Parts are immutable directories on disk. Background merges combine them. Insert one row at a time, faster than merges can keep up, and you hit the famous Too many parts error. Either batch on the client or turn on async_insert=1 so the server batches for you.

The picture

table
 ├── part_2026_06_1_1_0/        ← immutable directory, one per INSERT (until merged)
 │     ├── site_id.bin          ← each COLUMN is its own compressed file
 │     ├── event_time.bin
 │     ├── ...
 │     └── primary.idx          ← SPARSE index: one entry per 8192 rows ("granule")
 ├── part_2026_06_2_2_0/
 └── ...                        background merges combine parts forever


query:  WHERE site_id = 42 AND event_time > now() - 7d

ORDER BY (site_id, event_time)         ORDER BY user_id

└──┴──┴──┴──┴──┴──┴──┴──┘              └──┴──┴──┴──┴──┴──┴──┴──┘

Every optimization you'll learn — codecs, dictionaries, materialized views, projections, the query cache, the Null engine, ASOF JOIN — is a way to read fewer columns, skip more granules, or avoid the work of merging. Everything else is detail.

3 · Why each exercise exists

What you'll be able to do after each one.

Each entry below: what you'll learn and the concrete capability it gives you. If you skip an exercise, this is the capability you don't have.

Lab fundamentals — the bedrock

01

ORDER BY — the biggest single win

Two tables, 20M rows each, identical query — 100× difference in elapsed time. You'll see the granule-pruning mechanism for the first time.

After this: when you design a table, you'll know which column goes first in ORDER BY and why time usually goes last.

02

Types, LowCardinality, codecs

Compare per-column compression for the two tables from 01. Build a third variant that beats both.

After this: you'll pick UInt16 over UInt64 by reflex and know which codec to layer in front of ZSTD for timestamps, gauges, and small ints.

03

Async inserts — the parts war

Run make storm-sync, watch Active parts climb to Too many parts. Run make storm-async, watch parts stay flat. Same 2000 rows, ~2000× fewer parts.

After this: you'll never deploy a producer that does single-row INSERTs without async_insert, and you'll know exactly which setting to flip.

04

Dictionaries

500-row dimension table, 20M-row fact table. JOIN vs dictGet: typically 3–10× faster, less memory.

After this: you'll stop reaching for JOIN when a dimension is RAM-sized and slowly changing. You'll know HASHED vs COMPLEX_KEY_HASHED vs CACHE.

05

Materialized views — cheap real-time

MV is an INSERT trigger, not a cached query. Pay aggregation once at write time, then dashboards read pre-rolled rows.

After this: you'll understand the entire near-real-time stack: async inserts → MV → tiny rollup reads. This is the architecture, not a feature.

06

Query tuning — PREWHERE, skip indexes, projections

The three reversible knobs that fix queries the ORDER BY can't satisfy. Plus EXPLAIN in five flavors.

After this: when "my second access pattern is slow," you'll know whether to add a skip index, a projection, or build a second table via MV.

07

TTL + rollups — the fixed-box doctrine

Why a single well-sized server has a known worst case — which is the thing autoscaling charges you to avoid knowing.

After this: you'll set TTLs by reflex, treat raw data as a debugging buffer, and put rollups behind the query cache.

Lab expert — what the engine looks like under stress

10

Engine anatomy expert

Parts on disk, granules, ProfileEvents, sampling profiler. Read your own C++ stacks in SQL.

After this: "ClickHouse is fast" stops being magic and becomes predictable. system.events + ProfileEvents are your superpower.

11

The merge machine expert

Freeze merges with SYSTEM STOP MERGES, watch the disease, release, observe the avalanche cleanup. Plus partition surgery (instant) and mutations (slow).

After this: "Too many parts" stops scaring you. You diagnose merge starvation in one query and know whether to add merge threads, fix inserts, or both.

12

Ingestion warfare expert

The throughput ladder (VALUES vs JSONEachRow vs Native vs INSERT SELECT) — your hardware's actual rows/sec ceiling. Plus the Null engine (swallow infinitely, store nothing, MVs still fire).

After this: you'll know your box's ceiling and how to design pipelines around it instead of fighting it.

13

Read warfare expert

Three caches you control. In-order aggregation that never builds a hash table. Sampling. Three ways to dodge FINAL. Aggregate projections — the rollup hidden inside the table.

After this: every Grafana dashboard you've ever loaded slowly is fixable from this exercise. The query cache alone is worth the read.

14

Isolation expert

Memory ceilings per role, quotas, priorities, the kill switch. The four-line doctrine for keeping a fixed box healthy.

After this: one analyst can't OOM your ingestion. Worst case becomes known instead of catastrophic.

Lab integrations — every external system is just a table

20

Pull anything integration

URL, S3, file, Postgres, MySQL, remote ClickHouse — all are table functions. Schema inferred. Aggregation pushed down. Plus clickhouse-local, the engine without a server.

After this: "build a connector" stops appearing on your roadmap. Integration is a FROM clause.

21

Kafka pipeline integration

Three CREATE statements: Kafka engine + MV pump + MergeTree. No separate consumer process.

After this: "streaming pipeline" stops being a project. The MV is your transformation layer in SQL.

22

Postgres sync integration

Four escalating patterns: live query, dictionary cache, refreshable MV, full CDC. Pick what your latency budget allows.

After this: you can wire OLTP-to-analytics in minutes instead of standing up an ELT framework.

Lab domain — where ClickHouse happens to be world-class

30

Tick store domain

Codecs were made for finance numbers. OHLCV bars as MV chains. ASOF JOIN — the killer feature that justified finance adopting CH.

After this: you'll understand why quant shops run their tick stores on this engine, and you'll be able to align multi-source feeds in one SQL statement.

31

ML features domain

Window functions for momentum/vol/z-score. Hash-based train/test split. Parquet export. Even an in-database SGD baseline as an honesty check.

After this: ClickHouse becomes your feature factory; Python/GPU does what it's good at (training). Feature logic lives in one place: SQL.

Playground — apply it to a real production schema

P-01

Understand the FINAL hotspot

All 982 production read.* views are SELECT * FROM ... FINAL. Measure the tax in ms, MB, and rows-read. Get the hit list of FINAL-heavy tables.

After this: you have receipts for the refactor PR. You know which tables are worth attacking.

P-02

Create dictionaries — for the §4a candidates

Three dictionaries on the small reference tables. Simple key + composite key examples.

After this: you've practiced both HASHED and COMPLEX_KEY_HASHED on a real schema. Total RAM cost: tens of KB.

P-03

Rewrite with dictGet

Mechanical before/after rewrites. Replace a derived view so 20 downstream consumers get faster at once.

After this: you've practiced the highest-leverage refactor — replacing views, not queries.

P-04

Benchmark

Side-by-side with labels, then one query against system.query_log for ms, MB, rows-read. The receipts.

After this: you can prove the refactor with numbers, not vibes.

5 · The pro checklist

What "knowing ClickHouse" looks like in production.

By the time you've worked through the relevant tracks, every item below should feel like a reflex, not a lookup.

Schema (decide once, pay forever)

  • ORDER BY matches the dominant filter pattern, low→high cardinality
  • LowCardinality, tight ints, no reflexive Nullable
  • Codecs on timestamps / counters / gauges
  • PARTITION BY monthly-ish, used for TTL/drops only

Ingestion

  • Batched inserts or async_insert=1 — never raw tiny inserts
  • Active parts panel flat or sawtoothing, never climbing
  • MVs lean; rollups chained (raw → 1m → 1h → 1d)

Queries

  • Dashboards read rollups, never raw
  • Dimensions via dictionaries, not JOINs
  • EXPLAIN indexes=1 shows real granule pruning
  • No SELECT * on wide tables
  • Query cache on dashboard queries

Cost / safety

  • TTL on raw data; recompress/tier old parts
  • Memory limits + quotas instead of autoscaling
  • system.query_log reviewed for the top offenders weekly
  • Ingestion path has reserved capacity (threads, memory)
6 · How to actually use this repo

The runtime side of "learning ClickHouse".

# One-time setup
brew install colima docker docker-compose
colima start --cpu 4 --memory 8 --disk 40

# Spin up the stack
make up                 # ClickHouse + Grafana
make seed               # lab dataset: 20M events
make playground-seed    # prod-replica dataset: ~750k rows

# The four browser tabs you want open
http://localhost:8123/play   # admin / admin — your SQL terminal
http://localhost:3000        # Grafana — admin / admin
file://.../lab/docs/exercises/index.html   # lab walkthroughs
file://.../playground/docs/index.html      # playground walkthroughs

# Optional: Kafka + Postgres for exercises 20-22
make up-integrations

# Optional: 2-node cluster + Keeper for exercises 40-45
make up-cluster
make cluster-status   # confirms wiring
make sql-1            # interactive client on ch-1

The exercises assume you have Grafana on a second screen. The Feedback Loop dashboard refreshes every 5 seconds. When you run make storm-sync, watch the Active parts panel — that's the lesson. Most exercises wire to a system table query that proves the result; the Grafana panels are the visual proof.

The one habit to keep. When you don't know why a query is slow, the answer is in system.query_log and system.parts. Open them first, hypothesize second. Every expert tool in this lab is downstream of that habit.
